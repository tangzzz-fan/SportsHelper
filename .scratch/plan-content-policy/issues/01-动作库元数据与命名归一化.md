# 01: 动作库元数据与命名归一化

**What to build:** 给动作库加「用途」维度，并让计划里显示的动作名一律取库内标准名。这是后续三个补库 ticket 的地基。

**Blocked by:** None (can start immediately)

**Status:** done（2026-10-24）

## 条目

- [ ] 新增 `ExercisePurpose`：`warmup` / `strength` / `stretch` / `mobility`
- [ ] `ExerciseEntry` 加 `purposes: Set<ExercisePurpose>`，默认 `[.strength]`
- [ ] 18 个现有动作补齐：开合跳、高抬腿、登山跑标 `[.warmup, .strength]`，其余 `[.strength]`
- [ ] `PlanImportService.parse` 外层加一次名称归一化：`item.name` 一律取 `ExerciseLibrary.entry(item.catalogId)?.name`；库外动作保留原名
- [ ] 剂量口径：`purposes` 只含 `stretch` 时默认按秒，其余不变（不硬改模型已给出的 type）
- [ ] 单测：strictJSON / lenientJSON / freeText 三条路径产出的 name 都是库内名
- [ ] 单测：同一 catalogId 配三种不同写法（「死虫」「死虫式」「Dead Bug」），产出同一个 name

## 为什么必须在 service 层

`PlanDraftCompiler` 第 139 行已经是 `entry?.name ?? ...`，但 **strictJSON 路径不走它**——`PlanDecoder.decode` 直接解出 `WorkoutPlan`，name 就是 JSON 原文。实测里「哑铃肩推」「死虫式」都来自这条路。

所以归一化放在 `parse` 外层，一次覆盖三条路径，而不是在每个 decoder 里补。

## 验收

重新采样 8 个场景，「死虫 / 死虫式」这类同物异名归零；`ExerciseLibrary.all` 的每个动作都能报出自己的 purposes。
