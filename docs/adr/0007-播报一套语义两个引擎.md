# 播报：一套语义，两个引擎

**Status:** accepted（2026-10-25）

审计先定了性：文案层与闸门层的分层是对的（`DongKeCore` 不 import AVFoundation，61 条单测），但「什么时候说、一拍说几句、说不下怎么办」没有模型。结果休息归零在同一个 tick 连发两句，实测 8.79 秒；同一份代码，主线程晚 60ms 就变成第一句被切在 0.11 秒。**在换引擎之前必须先有话句语义**，否则神经引擎 100–800ms 的合成延迟会把同一个缺陷放大成「所有指令排队堆积」。

## 决定

1. **一拍一句。** 休息归零不再「先报休息结束、再报下一组」，合并成一句「俯卧撑，第 3 组，共 3 组，12 次」。省 4.2 秒，信息不重复。只有没有下一组时才念「休息结束」。
2. **预算按秒，不按字。** 单句 ≤4 秒（实测 4.0–4.3 字/秒；组开始最短也要 3.8 秒，3 秒做不到）。超了先丢「共 N 组」，再丢预告；动作名与剂量最后才动。删掉 `textLimit = 40`——换算过来是 10 秒，等于没有上限。实现落在 `WorkoutAnnouncement` 的 `*Budget`，超预算先丢「共 N 组」。
3. **触发面收窄。** 动作中只留两类：中段一句要点、最后 3 秒倒数。删「时间到」的语音（计时归零已由系统音 + 触觉表达，再念是四声重复）；删「加油」（`allowsEncouragement` 从未被置 true，是死代码，且语气与「给出口」的产品立场不符）。
4. **端口从「喇叭」改成「话句」。** 现有 `SpeechAnnouncing` 只有 `isSpeaking / speak(String) / stop()`，没有句柄、没有事件、没有可用性、没有音色档案、没有线程模型。神经引擎需要的这五样它都装不下。新端口 `SpeechRendering` 带 `SpeechRequest`（id / priority）、`SpeechOutputEvent`（started / finished / cancelled / failed）、`SpeechAvailability`、`SpeechProfile`。**不做 deadline**：既然一拍一句、不排队，过期就没有作用面；要停靠 scenePhase。
5. **会话只有一个 owner。** 播报与收音现在各自对 `AVAudioSession.sharedInstance()` 调 `setActive(true/false)`，靠「两个功能不同屏」维持正确。收进 `AudioSessionArbiter`，引用计数。
6. **音色先于引擎。** 现有代码只传 `language: "zh-CN"`，拿到的是系统默认音色；本机实测返回 compact Tingting，而同一台机器装着 premium 的「声音2」。先按 `quality` 选已安装的最高档，并在设置页显示当前音色名。
7. **换引擎要三条同时成立**：商用许可干净、iPhone 上 RTF < 0.5、体积可接受（随包或按需下载）。缺一条不做。

## Considered options

- **只调 rate / 加停顿标点。** 零成本，但改不了音色，也解决不了 8.79 秒。
- **Kokoro-82M。** 音质好、权重 Apache-2.0，但中文在 iPad 上 RTF 1.5–1.8（比实时慢），中文 G2P 依赖 eSpeak-NG（GPL-3.0）——闭源上架是许可毒丸。
- **Matcha-icefall-zh-baker。** 速度快、体积小，但训练语料 DataBaker 明确「仅限非商用」，sherpa-onnx 文档自己挂了 Caution。
- **vits-icefall-zh-aishell3。** Apache-2.0、29MB、RTF 0.16，许可与性能都干净，但 8kHz 窄带——音质低于系统 premium 音色，换了不赚。
- **MeloTTS zh_en（sherpa-onnx）。** MIT、44.1kHz、163MB，是唯一「许可干净 + 音质高于系统 compact」的候选，但 RTF 在树莓派上 2.5，必须先在 iPhone 上实测首音延迟。
- **随包 vs 按需下载。** 随包 +160MB 伤安装转化；按需下载要多一套进度 / 失败 / 回退，但保住「打开就开始」，且换音色不用发版。选按需。

## Consequences

- Core 新增 `SpeechRequest` / `SpeechOutputEvent` / `SpeechRendering`，删除 `isSpeaking` 轮询；App 新增 `SystemSpeechRenderer`、`AudioSessionArbiter`，`SystemSpeechAnnouncer` 退化成纯适配器。
- 测试口径从「送了什么文本」升级为「一拍最多一句 + 每句 ≤3 秒 + 过期不念」。出声层仍然只能靠真机，这条缺口写在明处。
- `WorkoutVoiceSessionTests` 里「后一句由引擎打断前一句」的用例名与真实行为相反（实测同 tick 是排队），随端口重画一起改写。
- 神经引擎进 1.x 的前置是 `06-神经引擎试点` 的三条门槛；未过则永久停在「系统音色最高档」，这不是失败，是结论。
- 与 ADR-0001（不用 AI 也要能开始）一致：音色是增强项，模型缺失时系统 TTS 永远可用。

## 增补：真机首测后的三处修正（2026-10-25）

首测反馈「3/2/1 倒计时有问题」。查下去是三个独立的坑，都在出声层而不是文案层：

1. **删掉 `SpeechPriority.countdown`。** 原意是让倒数压过组开始，实际后果反过来：倒数「1」还没念完时，下一组的 `setStart` 优先级更低（`1 < 2`），`announce` 直接 return，**整句被丢掉**——听感就是「3、2、1……然后静默」。现在倒数与组开始同为 `instruction`，**同级别后到者赢**。优先级只剩两档：`aside`（可说可不说）与 `instruction`（现在必须说）。
2. **整节课按住音频会话。** 渲染器原来每句 `borrow` → 说完 2 秒 `give`，60 秒休息里会话早就归零，倒数第一声要在 `speak()` 前几微秒才 `setActive(true)`。真机重新激活 100–300ms，短句会被吞头甚至整句。改成 `VoiceService` 在课程期间持有一份租约，渲染器按句借还只是叠在它上面。
   ——GymMane（Flutter，无 TTS）用「循环播放一个 0.5 秒静音文件」达到同样目的：`Beeper._holding` 每响一声就把会话按住 1600ms。同一个问题，两种解法。
3. **排除趣味音色。** `speechVoices()` 里挂在 `zh-CN` 下的不只有婷婷，还有 Eddy / Flo / Grandma / Grandpa / Reed / Rocko / Sandy / Shelley / Li-mu / Yu-shu 十个 `isNoveltyVoice`。原来只按 `quality` 取最大，取到「老奶奶」也会照念。本机模拟器实测：过滤后只剩 `Tingting(q1)` 一个候选。**这条同时说明模拟器上永远听不到增强音色**，音色验收必须真机。

## 增补：一课一嘴（2026-10-25）

验收反馈「点『提前练一次』出现两个音频」。日志里同一句 `开始训练，上肢与核心` 被送进渲染器**三次**（一次被取消、两次念完）。四个原因，全部在「谁拥有出声权」这一层：

1. **播报会话挂错了生命周期。** `WorkoutVoiceSession` 由 `WorkoutView` 自己持有：`onAppear` 新建、`onDisappear` 置空。fullScreenCover 的呈现动画会成对触发这两个回调——实测同一节课 `onAppear` 触发**三次**（日志里三条 `policy`，同时 `deactivate → activate` 一整轮）。每次新建都会再念一遍开场。
2. **t=0 就有两句。** `start()` 先念开场，紧接着 `stepChanged(to: 0)` 念第一组，同一 tick 里后到者把开场拦腰截断。用户听到「开始训练，下……」然后立刻换句。
3. **每个协调器一个新引擎。** `VoiceService` 每次 `activeCoordinator()` / `preview()` 都新建渲染器，也就是新的 `AVSpeechSynthesizer`。多个 synthesizer 各自排队，上一句没念完就 `speak` 下一句时会**依次念完**——这是字面意义的「两个音频」。
4. **`cancel()` 用 `isSpeaking` 当开关。** 这个判断在 `speak()` 返回瞬间还是 false，于是 `stopSpeaking` 被跳过：以为停了，其实还在念，音条同时开始播。

**决定：**

- 播报会话的归属是**一节课**，不是视图。`VoiceService` 按 `sessionId` 缓存，视图重建多少次都拿回同一个实例；`start` 每实例只生效一次（`didStart`），`stop` 之后也不会重念开场。
- **第一拍是组时，开场让位。** 一拍一句在 t=0 同样成立：只念「深蹲，第 1 组，共 4 组，12 次」，当天主题交给屏幕。首步不是组的计划（休息日）仍然念开场。
- **恢复训练不念开场**（`stepIndex > 0`）。
- 全 App **一个渲染器**；`render` 入口先停上一句，`cancel` 无条件 `stopSpeaking`。
- `.inactive` 算前台。下拉控制中心、来电横幅、转场都会短暂 inactive，把它当后台会让播报在转场瞬间被掐断，并连带释放/重建音频会话。

**代价：** 训练日不再有「开始训练，X」这一声；这是有意的——它原来只播出了半句。要恢复整天主题的口播，得先给它一个独立的拍（例如开场前加 1 秒静默），那属于产品决策，不在本次范围。


## 增补：播报里不得出现自由文本（2026-10-25）

音条（阶段 0）上线后做了一次覆盖实测：取 24 句真实播报喂给 `VoiceClipBank`，**12 句回落系统 TTS**。逐条核对可达性，真正会出现在播报链路上的只有两类，但两类都致命——它们让一节课里出现**两种音色**，于是「拼接好不好」这个判据根本无法成立。

| 来源 | 为什么录不了 | 频率 |
|---|---|---|
| 开场句的当天主题名 | AI 生成（"上肢与核心"、"全身循环"），无界 | 休息日每节 1 句 |
| 标准档的动作要点 | 自由文本，但**有界**：50 个动作 × 每条 2–3 句，共 150 条 | 静力动作首组，1 句 |

顺带被新守卫抓到的两个洞（不是设计问题，是漏录）：`durationText` 整分钟输出「N 分钟」而词表只有「N 分」，于是**默认 60 秒休息整句回落 TTS**；开场句的「N 个动作」也没录。

**决定：**

1. **播报文案只允许由封闭词表构成**——动作名、剂量、数字、固定词。任何 AI 生成的字符串（主题名、区块名）不得进句子。要看主题，屏幕上一直写着。
   - `WorkoutAnnouncement.sessionStart` 去掉 `title` 参数，改成「开始训练，共 9 组，3 个动作」。参数留着而不用，是对读代码的人撒谎。
   - `blockBreak` 的 `nextLabel` 本来就是「动作名 + 剂量」（**不是**区块标题），所以它天然可切，不用改。
2. **动作要点全部入词表**（150 条）。它们来自动作库、条数有限，是内容而不是自由文本。代价：动作库扩容时要重跑 `scripts/render-voice-clips.sh`。
   要点比别的句子长（最长 23 字 ≈ 5.5 秒），因为它**不是时间关键拍**——它落在动作中段，说完就说完；而「组开始 / 休息归零」这类句子必须 ≤4 秒。`.focus` 因此不走 `compose` 的预算，改由一条测试守住「每条要点 ≤24 字」。
3. **加一条守卫测试**：走一遍「循环 + 多区块」计划的所有播报（开场、每组、要点、休息、跨区块、倒数、完成）与全部动作要点，断言 `VoiceClipBank.plan(for:)` 都是 `.clips`。这条测试写完当场抓到上面两个漏录——它比人读词表可靠。

**代价：** 训练日与休息日都不再口播当天主题；动作库加动作后必须重渲染音条，否则新动作的要点会回落（守卫测试会红）。

**与 06 的关系：** 音条方案成立之后，设备内实时 TTS（票 06，MeloTTS + sherpa-onnx，163MB）**不再有必要**。它原本要解决的问题是「系统音色僵硬」，而音条走的是离线渲染 + 运行时拼接，绕开了 RTF、体积与设备内推理。06 转为「若音条被判死才重启」的备用路线，不再排在 07 之前。
