# 剂量回路（Dose Loop）

> 2026-10-25 · 依据 ADR-0003 / ADR-0004 · 词表见 `GLOSSARY.md`
> 状态：**12 张票全部落地**（2026-10-25）。seam：`DoseAdjustment.propose(DoseContext)`；上下文装 plan / logs / memory / sessionStarts / asked / now

## 问题

我照着这份计划练了三周。第一周每组都做完，第二周开始有两组做不完，第三周我干脆没开始。

App 一直在提醒我，但它给我的还是第一周那份计划——同样的组数、同样的次数、同样的重量。它不知道我变了，也不会因为我的记录改变什么。到第四周我不再点开通知了。

它记下了我每一次跳过，还让我选原因。它一个字都没用上。

## 方案

每周，App 看一眼我上周实际做了什么。

如果它认为该变，就把改动摆出来：哪个动作、从几组改成几组、为什么。**我点「就这样」它才生效；我不点，计划一个字都不动。**

加量的时候它说得像进展，减量的时候它说得像调整。都不会让我觉得是被削弱。

如果我连说三次「不用」，它就不再来问。

如果我两周没来，下次打开时它不等我点，先把第一课减半——因为那时候我需要的不是完整计划，是一个能完成的开始。

## 用户故事

### 提案怎么产生

1. 作为一个练了三周的用户，我想让 App 看我上周的实际完成情况，而不是永远给第一周那份计划，这样我才不会在第四周放弃。
2. 作为一个连续两次把某个动作的全部组都多做了 2 次的人，我想它建议我加量，这样我的进步能被看见而不是我自己拿本子记。
3. 作为一个连续三次选了「没时间」的人，我想它建议我少排一个动作，而不是建议我少做几组——因为问题在总时长，不在强度。
4. 作为一个连续两次选了「太累」的人，我想它建议我降一点重量，但别减组数，这样刺激量还在。
5. 作为一个选了「没有器械」的人，我想它建议换一个动作，而不是把这一项删掉。
6. 作为一个上周有动作做到疼的人，我想它这一次就建议降量，不用等第二次——疼和累不是一类信号。
7. 作为一个每次训练只有 20 分钟的人，我想它在动作数超过 5 个时优先砍动作而不是砍组数，这样我能在预定的时间里做完。
8. 作为一个刚开始练两周的人，我想它在我只练了 1 次的时候不要给任何建议，因为一次说明不了什么。
9. 作为一个练得很好但已经有四周没加量的人，我想它别每周都改我的计划，改得太勤我记不住自己练到哪儿了。

### 提案怎么呈现

10. 作为一个看到计划变了的人，我想知道**具体改了什么**（深蹲 3 组 × 10 次 → 3 组 × 12 次），而不是「计划已优化」。
11. 作为一个看到计划变了的人，我想知道**为什么**，而且理由要引用我自己上周做过的事，不是泛泛的「根据你的表现」。
12. 作为一个看到计划变了的人，我想在那个数字旁边看到说明，而不是要翻到总结页去找。
13. 作为一个看到加量建议的人，我想它写得像进展（「上一阶」），而不是像补偿（「补偿你上周的努力」）。
14. 作为一个看到减量建议的人，我想它写得像调整（「这周这样更合适」），而不是像道歉（「不好意思给你减轻了」）。
15. 作为一个不想改的用户，我想能一个动作就拒绝，不用填理由。

### 采纳与拒绝

16. 作为一个采纳了提案的人，我想计划立刻生效，且**这次训练就开始用新数字**，不用等到下周。
17. 作为一个拒绝了的用户，我想它不要下周再提同一条建议，否则我会觉得它没在听。
18. 作为一个连续拒绝三次的用户，我想它停一段时间不再提案，让我自己练。
19. 作为一个采纳过提案的人，我想在计划页看到「第 3 版」这样的标记，这样我知道这份计划和上周不一样是有原因的。

### 停练与重建

20. 作为一个连续两个训练日没开始的用户，我想下次打开时它先给我一节课，只有原来的动作数和组数的一半，而不是弹一个「欢迎回来」。
21. 作为一个完成重建课的人，我想下一周回到停练前的八成，而不是直接回到满量。
22. 作为一个只是漏了一次的用户，我想它**不要**给我重建课——漏一次和停练不是一回事，把小事当大事会让我觉得被小看。

### 归属与权限

23. 作为一个把教练给的计划粘进来的用户，我想 App **不要**主动改它，只在我要的时候给一条建议——因为那份计划有它的道理，可能是教练故意安排的低量周。
24. 作为一个用 App 自己生成的计划的人，我想它主动每周看一眼，因为我本来就不会自己去问「我该加量了吗」。
25. 作为一个把 AI 计划粘进来的人，我想它仍然提醒我「AI 可能写错」，同时**不要**一边提醒我别信一边又主动改它。
26. 作为一个想知道计划来源的人，我想在计划页看到它是「App 排的」还是「粘贴进来的」，因为这决定了我该不该相信它。

### 数据采集

27. 作为一个在某组多做了 3 次的人，我想能记下「多做」，因为不记的话 App 永远不知道我能加量了。
28. 作为一个做完最后一组的人，我想用一秒钟选一个「还有几次余力」，不想每组都答题。
29. 作为一个不想被问的人，我想能跳过这个自评，且跳过不影响任何已有功能。

## 实现决策

### 个体化模型：三层分工

回路的判断依据分三层（ADR-0005）：**能力**决定剂量，**耐受**决定节奏，**偏好**只决定动作选择。**偏好不进剂量公式**——它一旦进公式，个体化立刻退化成迎合。

| 层 | 决定什么 | 从哪读 | 落在哪张票 |
|---|---|---|---|
| 能力 | 剂量：做多少 | `actualValue` 超目标 + `rpe` | 02 / 04 |
| 耐受 | 节奏：多快加 | 加量后第几次出现降阶或跳过 | 12 |
| 偏好 | 路径：换哪个动作 | 总被跳过的动作、删除记录 | 纠错线，不在本 spec |

**耐受层的读法**：每次加量被采纳后，记「第几次训练出现降阶或跳过」。连续两次加量都在第 1 次崩 → 幅度减半；都撑过第 3 次 → 幅度用上限；其余保持默认。

**为什么耐受要单独一层**：同样是加 2.5kg，有人没事，有人崩。固定 2.5% 是规则，「你的崩点在第二次」才是模型。它也是 ADR-0005 里「预测误差在缩小」的主要来源——能力层只解释「能做几个」，耐受层才解释「能撑多久」。

### 一个纯函数，一个 seam

新增 `DoseAdjustment`（`DongKeCore/Workout/`）：

```
propose(plan: WorkoutPlan, logs: [SetLog], sessions: [WorkoutSession], now: Date) -> PlanProposal?
```

`nil` 表示「这周不提」。**没有第二层返回码**——数据不足、刚拒绝过、外来计划未被询问、无需变更，对调用者都是同一个含义：沉默。区分它们只会让调用者去写不需要的分支。

`DoseAdjustment` 只 import Foundation，不碰 SwiftData。所有规则在里面，调用者只负责喂数据和展示。

### `PlanProposal`

```
PlanProposal { kind, changes: [Change], reason: String, createdAt }
Change { catalogId, name, field: .sets|.reps|.load|.exercise, fromValue, toValue }
```

`kind` 四值：`dose` / `rebuild` / `swap` / `safety`。`reason` 是一句人话，必须引用具体记录（「上周三组都多做 2 个」），不允许写「根据你的表现」。

**一周只出一个提案，但一个提案可以改多处。** `kind` 冲突时按优先级取一个：`safety` > `rebuild` > `swap` > `dose`。理由：分成两条提案，等于同一次打开要用户连点两次「就这样」，而其中一条还是「你上周疼过」——那不该被排在加量后面。

`Muscle` 九值：股四头 / 腘绳 / 臀 / 小腿 / 胸 / 背 / 肩 / 臂 / 核心。**臂不拆肱二肱三**，且**复合动作只计主肌群，不计次要肌群**。这两条是一起的：拆了就要把划船算成背 + 肱二，而肱二的剂量永远不够，App 会一直建议加手臂——过细的建模会产出错误的建议，而不是更准的建议。

**肌群覆盖度闸门**：某肌群在库里可用动作少于 2 个时，该肌群不产出 `dose` 提案，只记录。当前实测：腘绳只有「哑铃罗马尼亚硬拉」1 个、小腿只有「提踵」1 个——这两处在补齐前保持沉默。理由：只有一个动作可加，回路会把组数一路堆到那一个动作上，越过单动作上限，而它看起来还像是「医嘱」。

### 三条现有字段的语义变更

| 字段 | 现在 | 之后 |
|---|---|---|
| `SetLog.actualValue` | 恒等于 `plannedValue` | 允许 > 目标（多做 1–3 次）；降阶仍为一半；跳过为 0 |
| `SetLog`（新增）`rpe` | 休眠，永远 nil | 当天最后一组问一次，5 档，可跳过：1 很轻松 / 2 还能 3 次 / 3 还能 2 次 / 4 还能 1 次 / 5 力竭 |
| `ExerciseEntry`（新增）`primaryMuscles` | 无 | `Set<Muscle>`，47 条一次性补全；`ExerciseGroup` 三档保留不动 |

`rpe` 有两个用途，**两个阈值，不许合并**：

| 用途 | 阈值 | 为什么是这个方向 |
|---|---|---|
| 有效组（记账） | `rpe ≥ 2` 才算有效；`1 很轻松` 计入完成、不计入剂量 | 记账要**宽松**。少算会让回路以为「量不够，继续加」，而加过头伤的是依从性 |
| 加量判据（决策） | `rpe ≤ 3`（还能 2 次及以上）= 目标有富余，该加 | ACSM 2009：「能比目标多做 1–2 次，就加 2–10% 负荷」 |

一组可以**同时**算有效、又说明目标太低——这是两个问题：这组有没有构成刺激 / 这个处方是不是该变难。把两者合并成一个阈值，会让其中一半的判断出错。

### 加量的三步优先级

一次只动一个杠杆，顺序固定：

1. 目标次数未到该动作上限 → **加次数**（+2）
2. 已到上限且连续两次全组多做 ≥1 次 → **加负荷**（默认 +2.5%，幅度由耐受层调整，见上节），次数回落到下限
3. 负荷到顶（自重或已用最大档）→ **加组数**（+1，上限 +2 组）

触发条件统一为 ACSM 2009 的判据：**连续 2 次训练、同一动作全部组都能多做 ≥1 次**。单次不算。

### 减量的分支

| `skipReason` | 改什么 |
|---|---|
| `noTime` | 砍动作数（单次 > 5 时优先砍最末位的辅助动作），组数不动 |
| `tooHard` | 降负荷 5–10%，组数不动 |
| `pain` | 该动作降 20%，且**一次即触发**，不用连续两次 |
| `noEquipment` | 换动作（`alternativeId`），不降量 |
| `other` | 不动，只记录 |

`pain` 的即时处理（训练中「疼，停下」）不属于本模块，归 `WorkoutFlowModel`。本模块只处理**下周的降量**。

### 频率、拒绝与版本

- 一周一次，在周一（或下一个训练日）打开计划页时计算。**不是每次训练后**——剂量是周尺度概念，日尺度会变成噪音。
- 唯一例外：`rebuild` 在停练后第一次打开时立即出，不等周。
- 同一条提案（同 `kind` + 同 `catalogId` + 同 `field`）被拒绝后不再提。
- 连续三次拒绝 → 停止提案一个周期。
- `revision` 只在**采纳**时 +1。`PlanAdjustView` 的手动重排共用同一个计数器。

### 隐式周期，不加「第几周」

连续加量三周后，第四周自动降到 60%。不引入 `weekIndex` 字段，只记「上次降量是哪次会话」——显式周期要改 `PlanDay` 结构，而它带来的能力（跨周期进度追踪）不在本期。

### 延迟只采不判

`PlanDay.scheduledTime` 与 `WorkoutSession.startedAt` 都在，差值为延迟。本期**只记录，不参与判定**——阈值没有依据，先攒数据。

### 换动作即重置

`noEquipment` 换动作后，新动作的次数/负荷从该动作的下限重新开始，不做「动作等价类」迁移。新动作要重新学，历史剂量不该带过来。

## 反指标：怎么发现个体化跑偏了

正向指标（采纳率、完成率）在错误实现下**也会变好**。所以需要一组反指标，它们的特征是「看起来更好、实际更糟」：

| 现象 | 真实含义 |
|---|---|
| 跳过率下降，**同时**总剂量也下降 | 偏好进了剂量公式。是迎合，不是个体化 |
| 预测误差不变，但计划一直在变 | 在套规则，不是在学人。变的是措辞，不是判断 |
| 预测误差收窄，但降阶率上升 | 猜得准是因为猜得保守——它学会了「少给你一点」来保证命中 |
| 采纳率接近 100% | 提案太容易答应了。它在提用户一定会同意的事，回避真正需要的变更 |

最后一条最隐蔽：**高采纳率可能意味着回路在讨好，而不是在判断。** 一个有用的教练，他的建议里有相当一部分会被拒绝。

## 测试决策

- **唯一 seam**：`DoseAdjustment.propose` 这一个纯函数。Core 层，Swift Testing，构造 `SetLog` 序列断言 `PlanProposal` 或 `nil`。
- 只测外部行为：给输入、断言返回的 `changes` 与 `reason` 的关键片段，**不测内部规则函数的拆法**。规则怎么切是实现的自由。
- 需要覆盖的边界：数据不足（1 次训练）、连续两次才加量、`rpe ≤ 3` 不计剂量、五个 `skipReason` 各一条、`pain` 单次触发、动作数 > 5 时优先砍动作、外来计划返回 `nil`、拒绝记忆、连续三次拒绝后静默、`revision` 只在采纳时递增。
- 先例：`DongKeCoreTests/` 里的规则测试（`PlanRevisionTests`、动作库校验、`PlanSafetyChecker`）都是这个形状——纯输入、纯输出、无 I/O。
- 门禁：单文件 ≤500 行（不含空行）。

## 不在范围内

| 不做 | 原因 |
|---|---|
| AI 生成提案 | 一个 adapter 是假缝。现在只有本地规则，就不为「以后接 AI」抽象 |
| HealthKit / 心率 / HRV / 睡眠 | 破「纯 iPhone 零硬件」立场；sRPE 已够算负荷 |
| 显式周期（`weekIndex`、跨周期进度） | 要改 `PlanDay` 结构，收益不在本期 |
| 延迟判定阈值 | 无依据，先攒数据 |
| 动作等价类 | 换动作即重置，见上 |
| 训练中的即时安全停止 | 归 `WorkoutFlowModel`，不是计划变更 |
| `PlanAdjustView` 的视觉重做 | 只改文案（删「太难/太占时间」） |
| 自评（`rpe`）的详细输入 UI | 本期只做「1–5 档 + 可跳过」的最小控件 |
| ACWR / 单调性 / 应变指标 | ACWR 已被 Impellizzeri 论证应放弃；其余指标本期没有消费者 |
