## 0. 结论先行

| 结论 | 内容 |
|------|------|
| 一句话定位 | 动刻把 AI 写的运动计划变成「今天几点、做什么动作、做几组几次、休息多久」的执行日程——到点提醒，跟着做，做完打勾。 |
| 我们不做什么 | 不做课程库，不做 AI 生成引擎（只用用户自己的 Key），不做健身社区，不做饮食统计 |
| 核心差异化 | 市面产品在竞争「怎么生成计划」，没人竞争「生成之后怎么把它执行掉」。动刻只做后半段。 |
| MVP 四个能力 | （1） 获取与结构化（粘贴文本 / 粘贴 JSON / 直连 AI，经校正后生成周计划）（2） 提醒（**仅训练日提醒，每计划 ≤7 条**；久坐提醒降 P1）（3） 执行（逐组引导 + 组间休息）（4） 记录（打卡 + 完成率 + 历史） |
| 最大风险 | 导入三入口全失败导致激活断裂。三重兜底：直连 AI 生成 / 复制提示词去外部模型来回粘 / 校正页永远可手工保存 |
| 关键指标 | 计划导入后第 14 天仍在使用的比例 ≥ 50%；W1 单日完成率 ≥ 80% |

## 1. 问题陈述

### 1.1 谁，在什么场景，遇到什么痛

34 岁程序员，居家办公，每天久坐 8–10 小时，想减脂。他已经解决「不知道练什么」——用 ChatGPT 或 Claude 描述自己的条件（只有一对哑铃、每天 25 分钟、零基础），拿到一份看起来很合理的计划。

**问题出现在第二天。**

| 环节 | 现状（用户实际做法） | 为什么不行 |
|------|----------------------|------------|
| 计划存放 | 存在 ChatGPT 对话里 / 截图存相册 / 粘进备忘录 | 计划是一段散文。要边做边滑屏找「下一个动作是什么、做几组、休息多久」 |
| 时机触发 | 靠自己想起来 | 居家办公没有通勤、没有健身房动线，一天很容易整块滑过去。等他意识到「今天还没练」，已经是晚上 11 点 |
| 执行节奏 | 心里默数组间休息 | 数着数着被微信消息打断，休息 3 分钟，训练节奏崩了，剩下两组直接跳过 |
| 做不动时 | 没有出口 | 计划写了 12 个俯卧撑，做到第 6 个就力竭。他不知道该降级还是跳过，于是跳过，跳过三次之后再也没打开 |
| 第三周 | 对话被新对话淹没 | 计划在对话里活着，但执行记录不在。AI 不知道他上周漏了两次，于是「计划」变成一份静态遗物 |

### 1.2 为什么现有产品解决不了

- **Keep / Fitbod / Hevy Trainer 解决的是「生成」**：它们给你一个它自己算出来的计划。但用户的计划来自 ChatGPT——这是用户主动选择的、更贴合自己处境的东西，他不想换。而且这三家的差评恰恰指向「它算出来的计划不合理 / 感觉随机 / 做不下来」（详见 §4）。
- **ChatGPT / Claude 解决的是「生成」，明确不解决「执行」**：它记不住你上周漏了几次，也不能在你该练的时候通知你。这是产品形态决定的，不是提示词能补的。
- **提醒类 App 解决的是「泛化提醒」**：提醒「该运动了」，但不知道你今天的计划是「深蹲 4×12 + 休息 90 秒」。提醒和内容之间是断开的。

**市场空白：从「一段计划文本」到「一组可被逐条执行并被记录的行动」之间，没有任何产品做转换。**

## 2. 目标用户

### 2.1 主画像：居家减脂的程序员（MVP 唯一服务对象）

| 维度 | 描述 |
|------|------|
| 基本 | 34 岁，男性，互联网研发岗，已婚无孩或一孩 |
| 工作 | 全职居家办公（或每周 1–2 天到岗），日均久坐 8–10 小时，日均步数 < 3000 |
| 身体 | BMI 26–28，体脂偏高集中腰腹，无重大伤病史，可能有轻度腰颈劳损 |
| 器械 | 家里有一对可调哑铃（5–20kg）、弹力带、瑜伽垫，约 3–5 ㎡ 可用空间，无跑步机 |
| 时间 | 每天能挤出 20–30 分钟，时间段不固定（午休 12:30 或晚饭后 20:30 为主），会议随时打断 |
| 技术能力 | 高。已用 ChatGPT Plus 或 Claude，会用 JSON，能看懂 API Key 概念——**这是「BYOK 直连 AI」这条路径唯一现实的种子人群** |
| 关键行为 | 已经让 AI 生成过至少一次运动计划，执行 3–7 天后中断，此后反复重启 |
| 付费意愿 | 愿意为「省事」一次性买断或年付 ≤ 200 元；强烈反感开屏广告和「AI 功能单独收费」 |
| 值不值得做 | 付费意愿高、AI 使用习惯已成型、对结构化数据零恐惧——这三条同时成立的人群很窄，但恰好是 MVP 能跑通的唯一人群 |

**痛点权重（调研归纳）**

| 排序 | 痛点 | 现有方案覆盖度 |
|------|------|----------------|
| 1 | 到点时没人拉我，居家没有动线提醒 | 无（提醒 App 不知道计划内容） |
| 2 | 训练中要反复回看文本，节奏被打断 | 无（备忘录 / 截图） |
| 3 | 组间休息靠心算，被打断就崩 | 部分（Strong / Hevy 有休息计时，但需手动建 routine） |
| 4 | 做不动时没有降级出口 | 无 |
| 5 | 不知道自己坚持得怎么样 | 弱 |
| 6 | 不知道该练什么 | **已解决**（AI） |

### 2.2 次画像：产后恢复的女性（验证方向，MVP 不做专门适配）

| 维度 | 描述 |
|------|------|
| 基本 | 31 岁，产品/运营岗，产后 12 个月 |
| 器械 | 只有瑜伽垫 + 弹力带，通常没有哑铃 |
| 时间 | 碎片化，单次 10–15 分钟，孩子在场 |
| 心理 | 怕动作做错受伤，比起身材更在意「安全」；不能放声音、不能看视频 |
| 对产品的要求 | 需要「骨架图 + 要点 + 常见错误 + 低阶替代」的静态可读说明；需要「今天只能做 10 分钟」的计划压缩能力 |
| 对 MVP 的意义 | 她是「动作图形化提示 + 文字要点」需求的最强理由。但她的计划不是 AI 生成的，导入意愿低。MVP 仅保证可用，不做专门引导 |

## 4. 差评洞察

### 4.1 三条最关键的洞察

**洞察一：AI 生成计划的能力已经过剩，执行的系统性缺失才是断点。**

Keep 用户原话：「AI 模型和智障一样，制定的训练计划跟开玩笑一样，上来给 0 基础的人安排 K3 课程，**一节课都做不下来还谈什么坚持**？」Fitbod 用户：「每次练完都得自己再设计一遍动作，那我为什么还要付钱？」

这暴露的不是模型能力问题，是**能力匹配与降级机制缺失**。动刻的判断：不去和巨人比生成，而是承接用户已经信任的那个生成结果，把「做不下来」这件事在产品里解决掉。

**洞察二：计划的形式是错的——它是散文，不是结构。**

第三方分析的原话最准：「你的『计划』是一墙聊天文本。你在组间滑屏找下一个动作是什么，你没有上周举了多重的记录，三周后对话被淹没，计划就死了。」

这是纯粹的**数据格式问题**：AI 输出自然语言，执行需要 `{动作, 组数, 次数/时长, 组间休息}`。这个转换不需要模型能力——只需要解析能力 + 一个人工校正关口。这就是动刻的地基。

**洞察三：提醒的所有权错位——工具知道「该练了」，但不知道「练什么」。**

现有提醒要么是泛化的（「该运动了」，小米/Apple 的久坐提醒），要么被锁在某个内容库内部（Keep 的计划提醒只对你订阅的课生效）。用户自己的计划在 ChatGPT 里，于是任何 App 都无法为它设提醒。

反过来也成立：Strong/Hevy 知道你今天该做深蹲 4×12，但它们**不会在 20:30 提醒你**——它们假设你已经坐在健身房了。而居家办公的人，缺的正是那一下「被拉起来」。

### 4.2 补充洞察（影响设计决策）

| 洞察 | 来源证据 | 对产品的含义 |
|------|----------|--------------|
| 「必须买手表」是最高频的愤怒，且具有驱逐性 | Apple Fitness+ 社区：「我付了 Apple One 的钱，却因为不买表用不了这个服务」 | 纯 iPhone 可用是硬约束，Apple Watch 不进 MVP |
| 权益收缩比涨价更伤人 | Keep：拍照识热量从「不限次」变「每天三次」；AI 从免费变 798 元卡 | MVP 无任何付费墙；未来定价一次说清，不做「先免后收」 |
| 开屏广告是免费模式的最大代价 | 薄荷健康 9 月连续多条差评集中在开屏广告、虚假跳过按钮、摇一摇跳转 | 不做开屏广告 |
| 动作降级能力比动作库体量重要 | Fitbod：新手跟练受伤退出；ChatGPT 给 90kg 零基础安排引体向上 | 每个动作必须有「降阶执行」出口（减半次数 / 跳过 / 加时）；**动作替换推荐因架构 §18 出 MVP，降为 P1** |
| 加载失败会摧毁训练计划（不只是体验） | Keep 用户：「结果半天上传不上去，第二天锻炼也显示我没完成，打乱了训练计划」 | 核心执行流程必须离线可用，本地为唯一真源 |
| 记录类缺失最不可原谅 | Keep：「记录莫名其妙就退出了，等于没记」 | 每完成一组即落盘；训练中数据丢失 = 零容忍 |

## 5. 我们的差异化

> **用户为什么选动刻，而不是 Keep / Fitbod / ChatGPT / 备忘录？**

| **5. 零门槛、零广告、零硬件** | 纯 iPhone，无 Apple Watch 要求，无开屏广告，无账号，无付费墙 | 与 Apple Fitness+ / Keep / 薄荷的变现结构直接冲突 |

### 6.2 已决：直连 AI 进 MVP（v1.0 待决项关闭）

v1.0 建议将直连 AI 降为 P1。**架构冻结后此建议被覆盖**：直连 AI 进 MVP，且与粘贴导入为**并列一等入口**，不是主次关系。

我接受这个调整，理由记录如下（便于后续复盘时判断当时是否判断错了）：

| 我原来的顾虑 | 架构给出的化解 |
|--------------|----------------|
| 用户已有 ChatGPT 订阅，再填 Key 有双重付费感 | BYOK 用的是用户自己的额度，App 不收费；且提供了「复制提示词、贴到外部模型、再粘回来」这条零 Key 路径，等于同一份提示词服务两种人 |
| Effort 高、要处理 Key 存储与端点兼容长尾 | 三级 `response_format` 降级 + 错误分类已具体化到每条对应一句中文提示；Key 走 Keychain + 写入门禁验证 |
| 价值缺口在执行不在生成 | 成立，但**生成失败率必须有兜底**——如果只有粘贴一条路，用户第一次导入失败就没有第二次机会。三条入口互为兜底，激活成功率才是安全的 |

**反过来，我为这个调整付出的代价是**：§7.2 里「动作替换推荐」和「内置计划模板库」被移出 MVP（架构 §18），我会在 §11 风险里标注这是最先该补回来的东西。

## 7. MVP 范围

### 7.1 做（P0，必须全部完成）

#### F0 引导问卷（5 屏 / 10 字段）

字段与屏次（与架构 `UserProfile` 一一对应，10 字段分布在 5 屏）：

| 屏 | 字段 | 形态 | 默认值 |
|----|------|------|--------|
| 1 | 性别、年龄 | 分段控件 + 数字滚轮 | 男 / 30 |
| 2 | 身高、体重 | 数字滚轮（cm / kg） | 175 / 75 |
| 3 | 目标、训练水平 | 两个单选（减脂 / 增肌 / 耐力 / 一般体能 / 灵活性；零基础 / 中级 / 进阶） | 减脂 / 零基础 |
| 4 | 每周可训练日、单次时长 | 周一到周日多选 + 单选（10/20/30/45/60 分钟） | 周一三五 / 30 分钟 |
| 5 | 常练时刻、可用器械、伤病限制 | 时间选择 + 多选（自重/哑铃/弹力带/壶铃/单杠/其他）+ 自由文本 | 19:30 / 自重 / 无 |

规则：
- 每一屏都**预填默认值**，用户可以直接「下一步」一路走完，全程 ≤60 秒。
- 这 10 项全部是 AI 提示词输入，少一项生成质量降一档（架构 §8.3）。因此在**点「用 AI 生成」时**校验：若「器械」或「伤病限制」为空，弹一次确认「这两项影响计划是否适合你，确定不填？」——只提醒一次，不强制。
- **通知权限在第 5 屏选完提醒时刻、按「开始用」时请求**（FROZEN 决策 9 / 架构 D-25）；用户拒绝不阻塞，直接进计划获取页并在今日页显示权限说明条（见 §9.1）。v1.3 及以前写的「在提醒设置页才请求」已作废。

#### F1 / F2 / F3 三条获取入口（并列一等，无主次）

| 入口 | 需求点 |
|------|--------|
| **粘贴 · JSON**（主路径） | 用户粘贴符合 `plan-schema.json` 的 JSON。先做括号感知的 JSON 抠取（处理代码围栏 / 前后说明文字 / 字符串内大括号 / 尾随逗号 / 全角引号 / 外层数组包裹），再严格解码。严格 JSON 且零 issue 时，校正页按钮直接是「保存并使用」，不强制编辑 |
| **粘贴 · 文本** | 自由文本启发式解析，能认出至少 1 个动作即产出草稿，未识别字段留空并在校正页标黄。**成功标准刻意定得低：宁可让用户改 5 个字段，也不假装解析成功存进一份错计划** |
| **直连 AI（BYOK）** | 用户在设置里填 Base URL（强制 https）+ API Key + 模型名。Key 存 Keychain，只显示末 4 位，保存前发一次最小请求验证。生成走 `POST {base}/chat/completions`，`response_format` 三级降级，非流式，超时 60 秒，UI 显示进度可取消。同时提供「复制提示词」按钮——用户可贴进任意外部模型，把结果粘回来走 JSON 路径，**这是无 Key 用户的 AI 路径** |

三条入口共同的失败出口：**校正页永远可以手工添加动作并保存**。不存在「三条路都走不通」的死路。

#### F4 计划校正关口（必经）

- 除「严格 JSON + 零 issue」外，所有路径都进校正页。理由：计划是要照着练的，错一个组数就是错一次训练。
- `ParseIssue` 逐条定位到字段路径（如 `days[2].blocks[0].items[1].restSec`），点一下跳到对应编辑控件。
- 可编辑项：动作名、组数、目标值与类型、组间休息、每侧、删除、调整顺序、调整所属日。
- 保存前置校验：`days` 必须 7 项、`dayIndex` 不重复、`daysPerWeek` 与实际训练日数一致、组数 1–20、休息 0–600 秒、`scheduledTime` 为合法 HH:mm。

#### F5 结构化周计划 + 日程

- 计划恒有 7 条 `PlanDay`，休息日占位（`isRestDay = true`、`blocks = []`）。
- 日程按「周几 + 时分」重复，**不绑定具体日期**。
- 允许「今天跳过」不破坏后续排期（只影响当次 session，不改计划）。
- 切换计划：`PlanRecord.isActive` 同时只有一条为 true；切换用新计划，历史 session 保留旧 `planId` 归档。

#### F6 训练提醒

- 每个 `isRestDay == false` 且 `scheduledTime != nil` 的日子一条，提前 `leadMinutes`（默认 5 分钟）触发。无 `scheduledTime` 的训练日回退到全局默认时刻。
- 通知正文含：当天主题 + 主要动作与组数 + 预计时长。示例：标题「今天练下肢」，正文「深蹲 4 组、箭步蹲 3 组，预计 28 分钟」。
- 注册两个 `UNNotificationAction`：「已开始训练」直接深链执行页；「稍后提醒」延迟 15 分钟。
- 前台必须实现 `willPresent` 返回 `[.banner, .sound]`——默认前台不展示是「通知不生效」最常见原因。
- **单计划提醒条目 ≤7 条**。平台事实：iOS 单 App 待触发本地通知上限 64 条；架构为本期定的**常驻配额上限为 11 条**（架构 §13.4），本期实际只用到 ≤7 条，余量充足。

#### F7 久坐微运动提醒（v1.2 移出 MVP，降 P1）

> 项目总监裁决：本期不做久坐提醒。通知只保留训练日提醒，单计划 ≤7 条。

- 移出理由（裁决口径）：MVP 的提醒价值集中在「到点叫我练」，久坐提醒属第二优先场景，且会占用通知额度、分散对核心链路的注意力。
- 由此回收的额度：常驻只需承载训练日提醒 ≤7 条（架构配额上限 11 条），加训练中临时 1 条休息通知，额度不再紧张，删除 v1.1 的「27 条常驻」假设。
- 本期不做的连带项：设置页不出现久坐提醒开关（避免放一个不可用的开关）。
- P1 承接时沿用以下既有结论（保留备查，本期不实现）：间隔式提醒（每 60/90/120 分钟）在 64 条额度下不可行，需改为「工作日每天最多 4 个固定时刻」；因不读 HealthKit，文案不得写「你已经坐了 2 小时」，只能写「起来动 1 分钟」。

#### F8 逐组执行引导

- 进入执行页时把三层嵌套结构一次性展开为线性 `[FlowStep]`（动作 / 组 / 休息 / 换块 / 结束），同屏只显示当前一组：动作骨架图 + 3–5 条要点 + 组序号（2/4）+ 目标（12 次 或 30 秒 或 每侧 10 次）。
- 完成一组后自动进休息倒计时（环形进度 + 大字号剩余秒数 + 「+15 秒」「跳过休息」）。
- **锁屏与后台的准确表述**：App 进后台后进程被挂起，计时不再刷新。动刻的做法是休息开始时记录绝对结束时间 `restEndAt`，并在同一时刻排一条本地通知。因此对外表述统一为：
  - 应写：「休息结束时，锁屏也能收到提醒」
  - 不写：「锁屏继续倒计时」
  - 解锁回前台后，界面显示的永远是**按绝对时间重算的正确剩余**，不会从暂停处慢慢追赶。
- 做不动出口（常驻按钮，非隐藏菜单）：`减半次数` / `跳过本组` / `休息 +30 秒`。选完**立即生效，不做二次确认**（躺在地上多一次确认就是多一次放弃）。跳过原因枚举与架构 `SkipReason` 对齐：`没时间`（noTime）/ `太难做不动`（tooHard）/ `身体不适`（pain）/ `器械不在手边`（noEquipment）/ `其他`（other）。
- 休息归零后必须**自动**切到下一组（不等待用户确认）。自动切换后 3 秒内，底部出现一行「还没缓过来？加 30 秒」，3 秒后淡出。这不是阻止自动切换，是给「差两三秒」留一个口子；点它则回退到休息态并加 30 秒，不点则自然进入下一组。
- 时长型动作（平板支撑、开合跳计时）复用同一套计时状态机，不写第二套逻辑。
- 训练中置 `isIdleTimerDisabled = true`（防息屏），退出训练恢复。

#### F10 打卡 + 完成率 + 历史

按架构 §11 的口径**原样锁定**，开发与测试不得各自解释：

| 指标 | 定义 | 边界处理 |
|------|------|----------|
| 单日完成率 | `completedSets / plannedSets`，clamp 0…1 | **`plannedSets == 0` 返回空值，UI 显示「—」而不是「0%」**（休息日与失败日不能看起来一样） |
| 周完成率 | 该周完成训练日数 / 该周计划训练日数 | 分母为 0 显示「—」 |
| 连续达标天数 | 日完成率 ≥ **80%** 计为达标 | **今天还没练不算断链**，从昨天起算 |
| 中途放弃 | 保留已完成的组，`status = abandoned`，完成率**照算**，不特殊处理 | 理由：练了一半也是练了 |
| 周口径 | **固定周一到周日**，不跟随系统 `firstWeekday` | 必须与计划生成口径一致，否则跨周错位 |
| 计划组数分母 | 训练开始时 `plannedSets` 写死 | 中途改计划不影响本次分母 |

- 每组完成立即落库（不批量最后写）。允许连续撤销到本次训练起点。
- 汇总页与历史页除完成率外，必须**单独露出降阶率与跳过率**。理由：完成率 100% 会掩盖「四组都做了但每组减半」，只看完成率会让计划强度问题隐形。
- 历史页：按周展示完成率趋势（Swift Charts）+ 连续达标天数 + 每次训练的动作与组明细。

## 8. 验收标准（Given / When / Then）

### 8.1 引导与激活

- **AC-01** Given 首次安装且未完成引导，When 打开 App，Then 进入 5 屏问卷，每屏均有预填默认值，可连续点「下一步」不填任何内容直接走完，全程 ≤60 秒
- **AC-02** Given 用户走完问卷（器械选「自重」、时长 30 分钟、时刻 19:30、可训练日周一三五），When 点第 5 屏「开始用」，Then 系统**在该时点**请求通知权限；若用户拒绝，仍进入计划获取页，今日页显示「今晚 19:30 · 尚未导入计划」+ 唯一主行动按钮 + 顶部权限说明条，功能不被阻塞
- **AC-03** Given 问卷完成，When 冷启动第二次，Then 不再出现问卷，直接进今日页
- **AC-04** Given 问卷第 5 屏未填「器械」与「伤病限制」，When 点「用 AI 生成」，Then 弹一次确认「这两项影响计划是否适合你，确定不填？」，用户确认后可继续，不再二次打断

### 8.2 获取与结构化（核心链路）

- **AC-05** Given 用户粘贴一段含「哑铃深蹲 4组×12次，休息90秒」的自由文本，When 确认导入，Then 40 秒内（P95）展示校正页，其中一行明确显示「哑铃深蹲 / 4 组 / 12 次 / 休息 90 秒」
- **AC-06** Given 校正页有 5 个动作，第 3 个识别错误，When 用户把该行组数改为 3 并保存，Then 该行更新且其它行不受影响，日程使用修改后的值
- **AC-07** Given 用户粘贴的是一段无动作信息的散文（如「今天练一下胸吧，随便练练」），When 解析完成，Then **不报「系统错误」**，校正页提示「未识别到任何动作」并提供「填入示例」与「手动添加动作」两个出口
- **AC-08** Given 用户粘贴合法 JSON（`days[].blocks[].items[]`，每项含 `itemId/catalogId/name/sets/target/restSec/tempo/load/notes`），When 确认导入，Then 解码零 issue，校正页以「保存并使用」为主按钮，不做强制编辑
- **AC-09** Given 粘贴的 JSON 缺少 `restSec` 字段，When 解析完成，Then 走宽松路径成功，校正页显示 1 条 warning「缺少组间休息，已按 60 秒补齐」，可编辑后保存
- **AC-10** Given 用户已配置有效的 Base URL + Key + 模型名，When 点「用 AI 生成」，Then 显示进度指示与「取消」，60 秒内返回并进入校正页
- **AC-11** Given 用户把 Base URL 填成 `http://api.example.com`，When 点保存，Then 立即提示「接口地址需要以 https:// 开头」，**不发任何请求**
- **AC-12** Given 用户把 Key 填成 `sk-wrong`，When 保存，Then 验证请求返回 401，提示「API Key 被拒绝，检查是否填错或额度用尽」，**Key 未被保存进 Keychain**
- **AC-13** Given 模型服务不支持 `json_schema`，When 生成，Then 自动降级到 `json_object`，仍失败则降级到纯提示词，三次都失败时把错误码与原始响应（截断 500 字）交给界面，并提示「改用粘贴导入更稳」
- **AC-14** Given 用户不想填 Key，When 点「复制提示词」，Then 复制一段含完整 schema 约束与全部 18 个 `catalogId` 白名单的提示词，可粘贴到任意外部模型，结果可粘回 App 走 JSON 路径并成功
- **AC-15** Given 导入成功且可训练日为周一三五 19:30，When 保存，Then 今日页展示最近一个训练日的摘要（动作数、总组数、预计时长），非训练日则显示下一个训练日

### 8.3 提醒

- **AC-16** Given 已授权通知且今天有 19:30 的训练，When 到 19:25，Then 收到通知，标题为当天主题、正文含动作与组数与预计时长，点击直接进入执行页
- **AC-17** Given 今天是休息日，When 到达训练提醒时刻，Then **不发训练提醒**，且当天不产生任何训练提醒（久坐提醒本期不做，无其他通知来源）
- **AC-18** Given 用户已导入计划，When 统计全部待触发本地通知，Then 数量 ≤7 条且全部为训练日提醒；设置页**不出现久坐提醒开关**（本期不做，见 §7.1 F7）
- **AC-19** Given 用户拒绝了通知权限，When 回到 App，Then 今日页顶部出现说明条「未开启通知，到点不会提醒你」+「去开启」按钮，**今日页本身完整可用**、能看今天练什么并直接开始；该说明条与「无计划」空态共存（横条在上，空态从 pageTitle 起），与「休息日」空态不共存；用户点关闭后 7 天内不再出现
- **AC-20** Given 用户修改了计划的训练日，When 保存，Then 旧计划的提醒全部被移除、新计划按新时间重排，**不出现「旧计划残留 + 新计划叠加」**

### 8.4 执行

- **AC-21** Given 用户从通知进入执行页，When 加载完成，Then 立即显示「第 1 组 / 共 4 组」+ 动作骨架图 + 要点 + 目标「12 次」，无需任何额外点击
- **AC-22** Given 用户点「完成这组」，When 该组标记完成，Then 自动进休息倒计时（90 秒），环形进度在走，有「+15 秒」「跳过休息」两个按钮
- **AC-22A** Given 休息倒计时归零，When 自动切到下一组，Then 底部出现「还没缓过来？加 30 秒」，3 秒后淡出；若用户在 3 秒内点它，则回退到休息态并把剩余时间设为 30 秒；若未点，界面保持下一组执行态且**不得因该提示延迟自动切换**
- **AC-23** Given 休息倒计时开始，When 用户**立刻锁屏并等待 90 秒**，Then 锁屏期间收到「休息结束」本地通知；解锁后界面显示倒计时**已结束**（而不是剩余 30 秒），且不出现逐秒追赶
- **AC-24** Given App 在后台停留 10 分钟后回到前台，When 恢复，Then 一次刷新直接到「已结束」状态，剩余时间不为负
- **AC-25** Given 用户在第 2 组点「减半次数」，When 确认，Then 该组目标变为 6 次，状态记为「降阶完成」，**不影响第 3、4 组的目标值**
- **AC-26** Given 用户点「跳过本组」，When 未选原因，Then 阻止并要求从 `SkipReason` 五选一（没时间 / 太难做不动 / 身体不适 / 器械不在手边 / 其他），落地值分别对应 noTime / tooHard / pain / noEquipment / other
- **AC-27** Given 训练中 App 被系统回收，When 重新打开，Then 今日页显示「上次训练未完成」并提供「继续」/「放弃」；已完成组数不丢失，`plannedSets` 分母不变
- **AC-28** Given 用户完成最后一组，When 点「结束训练」，Then 汇总页显示单日完成率（`completedSets / plannedSets`，其中 done 与 downgraded 都计入分子）、**降阶率**、**跳过率**、总时长、跳过原因分布。三者缺一不可
- **AC-29** Given 今日是休息日（`plannedSets == 0`），When 查看今日页完成率，Then 显示「—」，**不显示「0%」**

### 8.5 记录与历史

- **AC-30** Given 用户完成率为 100%，When 回到今日页，Then 该训练显示已完成，连续达标天数 +1
- **AC-31** Given 用户昨天完成率 90%、今天还没练，When 查看连续达标天数，Then 仍显示昨天累计的数字，**不因今天未练而断链**
- **AC-32** Given 用户练到一半放弃，When 查看历史，Then 该次记录状态为「未完成」，完成率按已完成组数 / 计划组数计算，已完成的组在明细里可见
- **AC-33** Given 用户已切换新计划，When 查看历史，Then 旧计划的记录仍可查看，不受当前计划影响

### 8.6 动作提示

- **AC-34** Given 执行的动作在 18 个 `catalogId` 白名单内，When 查看动作卡，Then 显示 3 关键帧骨架循环（或「减弱动态效果」开启时的第 1 帧）、3–5 条要点、2–3 条常见错误、1 条低阶替代
- **AC-34A** Given 计划里有一个 `custom_` 前缀的库外动作，When 打开动作详情与训练页，Then 图示区显示通用灰色人形占位（**不是空白、不是错误图标、不是系统类别符号**），下方正常显示该动作的 `notes` 与「编辑这个动作」出口，且训练页可正常开始与打卡
- **AC-34B** Given 执行构建门禁，When 18 个 `catalogId` 中任一个的图示数据缺失，Then 门禁失败。**注意：这是构建门禁不是 UI 验收**。本方案下 18 个骨架全部自绘、无上游依赖，因此「18 个齐全」是硬要求，不存在「上游 slug 缺失算正常降级」的例外（该例外只属于已否决的口径 B）
- **AC-35** Given 执行的动作是 `custom_` 库外动作，When 查看动作卡，Then 显示计划里的 `notes` 文字要点 + 通用占位 + 「编辑这个动作」出口；**不出现「为你推荐相近动作」**（本期不做）
- **AC-36** Given 用户开启「减弱动态效果」，When 查看动作卡，Then 骨架固定第 1 帧不播放，但要点、常见错误、倒计时数字均正常显示与更新

## 9. 边界条件

### 9.1 状态覆盖（五态必达）

| 状态 | 场景 | 必须呈现 |
|------|------|----------|
| Loading | 解析粘贴内容 / AI 生成中 | 进度指示 + 已识别动作数递增（解析）或预估剩余（生成）+ 「取消」。AI 生成超过 60 秒自动中断并给重试。**「动作数递增」是表现层要求，不是解析器要改成流式**：解析仍一次性完成，UI 用逐行揭示 + 计数器同步递增呈现，观感一致且不破坏解析器的纯函数可测性 |
| Empty | **四个空态**：无计划 / 休息日 / 无历史 / 计划页无计划 | 四者的文案与主行动互不复用。**禁止 Lorem ipsum / "Welcome to" 类占位**。例：无计划 =「还没有训练计划。粘贴一段计划文本，或者用 AI 生成一份。」+ 主按钮「导入计划」；休息日 =「今天是休息日 / 下次训练：周四 19:30，下肢力量。」+ 主按钮「看本周安排」 |
| 说明条（**不是空态**） | 通知权限被拒 | 横条在页面顶部满宽、`warningSoft` 底色、带关闭按钮；今日页正文从 pageTitle 起排布，横条与空态形态不同、不会被看混。**与「无计划」空态共存；与「休息日」空态不共存**（休息日提醒开通知是纯噪音，直接不显示）。用户关闭后 7 天内不再出现 |
| Error | 解析失败 / Key 无效 / Base URL 非法 / 存储写入失败 | 分类说明原因 + 可执行出口（重试 / 改用粘贴 / 手动添加 / 去设置）。**不丢失用户已输入的内容**，不出现「出错了」 |
| Populated | 正常态 | 今日页只显示「今天要做什么」+ 一个主行动，其余折叠 |
| Edge | 超长计划（>50 动作）/ 极端取值 / 跨周 | 动作数超 50 提示「这份计划有 68 个动作，建议只导入本周的」；组数 >10 或休息 >600 秒在校正页高亮，提示可能是解析错误 |

### 9.2 逐项边界

| 类别 | 边界 | 处理 |
|------|------|------|
| 空状态 | 问卷跳完但无计划时直接进执行页 | 不允许。必须先进计划获取页 |
| 输入 | 粘贴内容 0 字符 / 超 64KB | 0 字符按钮置灰；超 64KB 直接拒绝并提示「内容过长，建议只粘贴每周的计划」（架构 §16 风险 8） |
| 输入 | 非法 JSON 片段 | 降级到文本启发式解析，不走报错 |
| 数值 | `sets` 为 0 或 >20、`restSec` <0 或 >600 | 校正页标黄并 clamp（`PlanNormalizer`），保存时提示已自动修正 |
| 数值 | `restSec` 缺失 | 默认 60 秒，校正页标注「已自动填充」 |
| 数值 | `target.value` 超出 1–3600 | clamp 并提示 |
| 数值 | `scheduledTime` 为「25:00」「7:5」 | 校验失败，要求重填 |
| 并发 | 执行训练中再次点通知 | 恢复到当前执行态，**不新建 session** |
| 并发 | 同一时段两个训练块 | 合并为一条通知：列出两个主题，进入后选择 |
| 通知额度 | 待触发通知接近架构配额上限 11 条（平台硬上限 64 条） | 先清 `dk.plan.` 前缀再排；按 weekday 从周一起截断并记 warning（架构 §13.4）。正常路径不可能触发 |
| 离线 | 全程离线 | 除直连 AI 外，全部 P0 可用；离线点「用 AI 生成」提示「需要网络，可以改用粘贴导入」 |
| 时区/跨天 | 用户跨时区 / 23:50 开始的训练跨 0 点 | 提醒按设备当前时区解释（跨时区后本地时间触发，这是想要的）；训练归属到开始日期 |
| 权限拒绝 | 通知被拒 | 见 AC-19，不阻塞任何功能 |
| 中断 | 训练中来电 / 收到其他通知 | 休息倒计时基于绝对时间戳，恢复后时间准确 |
| 中断 | 训练中低电量 / 后台被系统回收 | 每完成一组即落盘，恢复回到断点；已完成组永不丢失 |
| 数据量 | 累积超过 1 年记录 | 历史页默认显示最近 8 周，更早折叠加载 |

### 9.4 数据埋点方案（v1.1 重写：纯本地，不上报）

> **v1.0 的埋点方案前提是错的。** 架构 §18 明确「不做第三方分析 SDK、崩溃上报 SDK」，§1 明确「无账号、无自建后端」，数据只在本机。因此不存在「埋点上报到某处」这件事。重写如下。

**MVP 的埋点是三层，全部落地在本机：**

| 层 | 用途 | 落点 |
|----|------|------|
| L1 业务数据 | 直接支撑 KPI 计算，是产品事件本身 | SwiftData（`SessionRecord` / `SetLogRecord` / `PlanRecord`），不需要额外埋点 |
| L2 结构化事件日志 | 记录漏斗与失败点，用于事后归因 | 本地事件表 / OSLog 结构化字段，含 App 内「诊断数据」页可查 |
| L3 用户主动导出 | 内测阶段唯一的取数通道 | `BackupService` 导出 JSON，用户手动发给团队 |

**必须记录的事件（本地，命名 `{对象}_{动作}`）：**

| 类别 | 事件名 | 说明 | 关键属性 |
|------|--------|------|----------|
| 激活 | `onboarding_complete` | 问卷漏斗 | `completed_steps`、`used_all_defaults`、`equipment_count` |
| 激活 | `plan_import_attempt` | 发起导入 | `channel`（paste_text / paste_json / ai / manual）、`char_count` |
| 激活 | `plan_import_result` | 导入结果 | `channel`、`result`（strict_json / lenient_json / heuristic / failed）、`issue_count`、`parse_ms` |
| 激活 | `ai_generate_result` | AI 生成结果 | `response_format_level`（L1/L2/L3）、`error_code`、`elapsed_ms` |
| 激活 | `plan_saved` | 保存计划 | `source`、`days_per_week`、`total_sets`、`edited_rows`、`time_to_save_ms` |
| 执行 | `workout_started` | 开始训练 | `plan_day_id`、`planned_sets`、`started_from`（notification / today / manual）、`on_time`（是否在计划时刻 ±30 分钟内） |
| 执行 | `set_completed` | 完成一组 | `set_index`、`status`（done / downgraded / skipped）、`skip_reason` |
| 执行 | `rest_finished` | 休息结束 | `planned_rest_s`、`actual_rest_s`（衡量休息是否被打断） |
| 执行 | `workout_finished` | 完成训练 | `completed_sets`、`planned_sets`、`completion_rate`、`downgrade_count`、`skip_count` |
| 执行 | `workout_abandoned` | 中途放弃 | `last_set_index`、`completed_sets` |
| 提醒 | `notification_scheduled` / `notification_opened` | 提醒链路 | `kind`（plan / rest）、`lead_min` |
| 提醒 | `sedentary_snooze` | 久坐稍后（**P1，本期不埋**，久坐提醒已移出 MVP） | `snooze_count_today` |
| 异常 | `storage_write_failed` / `parse_error` / `key_validation_failed` | 异常 | `error_type`、`context` |

**约束**
- 每条事件固定带 `timestamp`、`app_version`、`os_version`、`device_model`；**不带** IP、不关联任何账号（无账号）
- 落盘形态：本地 JSONL，**保留 30 天**滚动清理（架构 `AnalyticsNaming` 白名单同时作为写入白名单，测试断言不写入原文类字段）
- **没有 `notification_delivered` 事件，不是漏做**：纯本地通知拿不到投递回执（`UNNotificationServiceExtension` 只对远程推送生效），只能采 `notification_scheduled` 与 `notification_opened`，两者之比即打开率。要投递级数据必须引入服务端推送，与「无自建后端」冲突，故不做
- **不上报**任何内容：原始计划文本、动作备注明细、伤病自由文本一律不进日志
- 提供「清除全部数据」（架构 §13），清除范围包含事件日志
- 不引入任何第三方 SDK。事件写入走 `AppLog` 封装

**KPI 怎么量（内测期的现实答案）**

没有后端就无法自动汇总。内测阶段（≤30 人）的取数方式是：用户从设置页「导出诊断数据」发给团队，团队聚合计算。这不是优雅方案，但它是当前架构约束下唯一诚实的方案，且足够验证「执行闭环是否提升坚持率」这个假设。若验证成立且需要规模化度量，P1 再评估是否引入自有后端——**而不是引入第三方 SDK**。

## 10. 成功指标

### 10.1 北极星指标

> **计划导入后第 14 天，该计划仍在被使用的比例（计划保鲜率）**

选它的理由：竞品的核心失败模式是「计划三周就死」（§4.1 洞察二）。如果用户导入计划后两周还在用，说明「结构化 + 提醒 + 逐组执行」这条链路真的解决了问题；如果两周就死，说明我们只是又一个好看的计划查看器。

### 10.2 分层指标

| 层 | 指标 | MVP 目标 | 为什么是这个值 |
|----|------|----------|----------------|
| 激活 | 问卷完成至成功保存计划的比例 | ≥ 55% | 三条入口互为兜底，低于 40% 说明所有入口都有系统性问题 |
| 激活 | 问卷全程用默认值走完的比例 | ≤ 40% | 高于此值说明问卷太长或默认值不合理，AI 生成质量会因此下降 |
| 激活 | 三条入口的使用分布 | 无目标，**只看分布** | 用于判断哪条该重点优化；若 Ai 占比 <15% 则 F3 的可发现性有问题 |
| 核心价值 | **计划保鲜率（W2）** | **≥ 50%** | 北极星，见 §10.1 |
| 核心价值 | W1 单日完成率中位数 | ≥ 80% | 低于 70% 说明计划与能力不匹配，需上线 F11/F13 |
| 核心价值 | 准点开始率（计划时刻 ±30 分钟内开始） | ≥ 60% | 衡量提醒是否真起作用。低于 40% 说明提醒设计（文案/时机）需重做 |
| 留存 | D7 留存 | ≥ 35% | 单人工具类 App 合理水平 |
| 留存 | 周活跃训练天数中位数 | ≥ 2 天/周 | 主画像自述 3 天/周，取 2 为可接受下限 |
| 体验质量 | 导入成功率（无需手工大改即可保存） | ≥ 75% | 低于此值导入体验不成立 |
| 体验质量 | 无 Key 用户中走「复制提示词」路径的比例 | ≥ 30% | 衡量零 Key 路径是否被发现 |
| 体验质量 | 周三留存时仍有计划的用户比例 | ≥ 60% | 中段衰减点，第 3 周是竞品的死亡线 |
| 体验质量 | 训练中途放弃率 | ≤ 20% | 高于 30% 说明强度或时长设计有问题 |
| 体验质量 | **训练中数据丢失次数** | **0** | 零容忍（Keep 差评证明这一点） |
