# 动刻（DongKe）产品需求文档 v1.0

> 产品形态：iOS App ｜ 阶段：MVP ｜ 撰写：许清楚（产品经理）
> 文档目的：锁定 MVP 范围与验收口径，供架构师与设计师据此展开方案设计

## 0. 结论先行

| 结论 | 内容 |
|------|------|
| 一句话定位 | 动刻把 AI 写的运动计划变成「今天几点、做什么动作、做几组几次、休息多久」的执行日程——到点提醒，跟着做，做完打勾。 |
| 我们不做什么 | 不做课程库，不做 AI 生成引擎，不做健身社区，不做饮食统计 |
| 核心差异化 | 市面上的产品在竞争「怎么生成计划」，没人竞争「生成之后怎么把它执行掉」。动刻只做后半段。 |
| MVP 三个核心能力 | ① 导入：把 AI 计划文本/JSON 变成结构化日程 ② 提醒：到点 + 久坐双重触发 ③ 执行：逐组引导 + 组间休息计时 + 打卡 |
| 最大风险 | 粘贴导入的摩擦（复制→切 App→粘贴）导致首次激活失败；缓解方案见 §9 |
| 关键指标 | W1 训练执行完成率 ≥ 80%；计划导入后 14 天仍在使用的比例 ≥ 50% |

## 1. 问题陈述

### 1.1 谁，在什么场景，遇到什么痛

34 岁程序员，居家办公，每天久坐 8–10 小时，想减脂。他已经解决「不知道练什么」——用 ChatGPT 或 Claude 描述自己的条件（只有一对哑铃、每天 25 分钟、零基础），拿到一份看起来很合理的计划。

**问题出现在第二天。**

| 环节 | 现状（用户实际做法） | 为什么不行 |
|------|----------------------|------------|
| 计划存放 | 存在 ChatGPT 对话里 / 截图存相册 / 粘进备忘录 | 计划是一段散文。要边做边滑屏找「下一个动作是什么、做几组、休息多久」 |
| 时机触发 | 靠自己想起来 | 居家办公没有通勤、没有健身房动线，一天很容易整块滑过去。等他意识到「今天还没练」，已经是晚上 11 点 |
| 执行节奏 | 心里默数组间休息 | 数着数着被微信消息打断，休息 3 分钟，训练节奏崩了，剩下两组直接跳过 |
| 做不动时 | 没有出口 | 计划写了 12 个俯卧撑，做到第 6 个就力竭。他不知道该降级成跪姿还是跳过，于是跳过，跳过三次之后就再也不打开了 |
| 第三周 | 对话被新对话淹没 | 计划在对话里活着，但执行记录不在。AI 不知道他上周漏了两次，于是「计划」变成一份静态遗物 |

### 1.2 为什么现有产品解决不了

- **Keep / Fitbod / Hevy Trainer 解决的是「生成」**：它们给你一个它自己算出来的计划。但用户的计划来自 ChatGPT——这是用户主动选择的、更贴合自己处境的计划，他不想换。而且这三家的差评恰恰指向「它算出来的计划不合理 / 感觉随机 / 做不下来」（详见 §4.2）。
- **ChatGPT / Claude 解决的是「生成」，明确不解决「执行」**：它记不住你上周漏了几次，也不能在你该练的时候通知你。这是产品形态决定的，不是提示词能补的。
- **提醒类 App 解决的是「泛化提醒」**：提醒「该运动了」，但不知道你今天的计划是「深蹲 4×12 + 休息 90 秒」。提醒和内容之间是断开的。

**市场空白：从「一段计划文本」到「一组可被逐条执行并被记录的行动」之间，没有任何产品做转换。**

## 2. 目标用户

### 2.1 主画像：居家减脂的程序员（MVP 唯一服务对象）

| 维度 | 描述 |
|------|------|
| 基本 | 34 岁，男性，互联网研发岗，已婚无孩或一孩 |
| 工作 | 全职居家办公（或每周 1–2 天到岗），日均久坐 8–10 小时，日均步数 < 3000 |
| 身体 | BMI 26–28，体脂偏高集中腰腹，无重大伤病史，可能有轻度腰颈劳损 |
| 器械 | 家里有一对可调哑铃（5–20kg）、弹力带、瑜伽垫，约 3–5 ㎡ 可用空间，无跑步机 |
| 时间 | 每天能挤出 20–30 分钟，时间段不固定（午休 12:30 或晚饭后 20:30 为主），会议随时打断 |
| 技术能力 | 高。已用 ChatGPT Plus 或 Claude，会用 JSON、能看懂 API Key 概念 |
| 关键行为 | 已经让 AI 生成过至少一次运动计划，执行 3–7 天后中断，此后反复重启 |
| 付费意愿 | 愿意为「省事」一次性买断或年付 ≤ 200 元；强烈反感开屏广告和「AI 功能单独收费」 |
| 值不值得做 | 付费意愿高、AI 使用习惯已成型、对结构化数据零恐惧——这是「导入 AI 计划」这条路唯一现实的种子人群 |

**痛点权重（调研归纳）**

| 排序 | 痛点 | 现有方案覆盖度 |
|------|------|----------------|
| 1 | 到点时没人拉我，居家没有动线提醒 | 无（提醒 App 不知道计划内容） |
| 2 | 训练中要反复回看文本，节奏被打断 | 无（备忘录 / 截图） |
| 3 | 组间休息靠心算，被打断就崩 | 部分（Strong / Hevy 有休息计时，但需手动建 routine） |
| 4 | 做不动时没有降级出口 | 无 |
| 5 | 不知道自己坚持得怎么样 | 弱 |
| 6 | 不知道该练什么 | **已解决**（AI） |

### 2.2 次画像：产后恢复的女性（验证方向，MVP 不做专门适配）

| 维度 | 描述 |
|------|------|
| 基本 | 31 岁，产品/运营岗，产后 12 个月 |
| 器械 | 只有瑜伽垫 + 弹力带，通常没有哑铃 |
| 时间 | 碎片化，单次 10–15 分钟，孩子在场 |

| 对 MVP 的意义 | 她是「图形化动作提示」需求的最强理由，但她的计划不是 AI 生成的，导入意愿低。MVP 仅保证可用，不做专门引导 |

## 4. 差评洞察

### 4.1 三条最关键的洞察

**洞察一：AI 生成计划的能力已经过剩，执行的系统性缺失才是断点。**

Keep 用户原话：「AI 模型和智障一样，制定的训练计划跟开玩笑一样，上来给 0 基础的人安排 K3 课程，**一节课都做不下来还谈什么坚持**？」Fitbod 用户：「每次练完都得自己再设计一遍动作，那我为什么还要付钱？」

这暴露的不是模型能力问题，是**能力匹配与降级机制缺失**。动刻的判断：不去和巨人比生成，而是承接用户已经信任的那个生成结果（他自己的 ChatGPT），把「做不下来」这件事在产品里解决掉。

**洞察二：计划的形式是错的——它是散文，不是结构。**

第三方分析的原话最准：「你的『计划』是一墙聊天文本。你在组间滑屏找下一个动作是什么，你没有上周举了多重的记录，三周后对话被淹没，计划就死了。」

这是纯粹的**数据格式问题**：AI 输出的是自然语言，执行需要的是 `{动作, 组数, 次数/时长, 组间休息, 备注}` 的数组。这个转换没有任何现有产品在做，且不需要模型能力——只需要解析能力。这就是动刻的地基。

**洞察三：提醒的所有权错位——工具知道「该练了」，但不知道「练什么」。**

现有提醒要么是泛化的（「该运动了」，小米/Apple 的久坐提醒），要么被锁在某个内容库内部（Keep 的计划提醒只对你订阅的课生效）。用户自己的计划在 ChatGPT 里，于是任何 App 都无法为它设提醒。

反过来也成立：Strong/Hevy 知道你今天该做深蹲 4×12，但它们**不会在 20:30 提醒你**——它们假设你已经坐在健身房了。而居家办公的人，缺的正是那一下「被拉起来」。

### 4.2 补充洞察（影响设计决策）

| 洞察 | 来源证据 | 对产品的含义 |
|------|----------|--------------|
| 「必须买手表」是最高频的愤怒，且具有驱逐性 | Apple Fitness+ 社区：「我付了 Apple One 的钱，却因为不买表用不了这个服务」 | 纯 iPhone 可用是硬约束，Apple Watch 只做 P2 增强 |
| 权益收缩比涨价更伤人 | Keep：拍照识热量从「不限次」变「每天三次」；AI 从免费变 798 元卡 | MVP 承诺的核心功能不上会员墙；定价模型一次性说清，不做「先免后收」 |
| 开屏广告是免费模式的最大代价 | 薄荷健康 9 月连续多条差评集中在开屏广告、虚假跳过按钮、摇一摇跳转 | 不做开屏广告。宁可不做免费增值，也不做开屏广告 |
| 动作降级能力比动作库体量重要 | Fitbod：新手跟练受伤退出；ChatGPT 给 90kg 零基础安排引体向上 | 每个动作必须带「低阶替代」；这是图形化提示的一部分，不是附加功能 |
| 加载失败会摧毁训练计划（不只是体验） | Keep 用户：「结果半天上传不上去，第二天锻炼也显示我没完成，打乱了训练计划」 | 核心执行流程必须离线可用，本地优先，同步是后台尽力而为 |
| 记录类缺失最不可原谅 | Keep：户外步行「记录莫名其妙就退出了，等于没记」 | 训练中一旦开始，进程不可被意外中断丢失；状态实时落盘 |

## 5. 我们的差异化

> **用户为什么选动刻，而不是 Keep / Fitbod / ChatGPT / 备忘录？**

| 差异化点 | 具体表述 | 竞品为何难以跟进 |
|----------|----------|------------------|
| **1. 我们承认你的计划是你的** | 不生成计划，只接管执行。你在 ChatGPT / Claude / 教练微信里拿到的任何计划，粘进来就变成可执行日程 | Keep/Fitbod/Hevy 的商业模式建立在「用我的计划」上，导入外部计划等于自毁内容与订阅价值 |
| **2. 计划进来就是结构** | 文本/JSON → 动作、组数、次数、组间休息的结构化数组，训练时不需要再读任何一段话 | ChatGPT 产品形态上不做结构化落库；记录类 App 不愿意做解析（投入重、场景窄） |
| **3. 提醒是有内容的提醒** | 通知写的是「现在：哑铃深蹲 4×12，休息 90 秒」，不是「该运动了」。点开直接到执行页第 1 组 | 提醒类 App 没有计划数据；内容类 App 的提醒绑定自家课程 |
| **4. 做不动有出口** | 每个动作带「降一阶」路径（标准 → 简化 → 只做一半组数）。执行中一键切换，不打断计时 | 竞品的降级是「视频里有个人做简化版」，需要你暂停、找、看、再开始 |
| **5. 零门槛、零广告、零硬件** | 纯 iPhone，无 Apple Watch 要求，无开屏广告，核心功能不进会员墙 | 与 Apple Fitness+ / Keep / 薄荷的变现结构直接冲突 |

## 6. 核心功能（RICE 排序）

RICE：`Score = (Reach × Impact × Confidence) / Effort`。Reach 1–10（季度受影响用户占比），Impact 0.25/0.5/1/2/3，Confidence 50%/80%/100%，Effort 1–10（人月）。

| ID | 功能 | Reach | Impact | Conf | Effort | Score | 优先级 |
|----|------|-------|--------|------|--------|-------|--------|
| F1 | 启动引导（器械 / 运动基础 / 单次可用时长 / 常练时段 / 久坐提醒开关） | 10 | 2 | 1.0 | 2 | **10.00** | P0 |

### 6.1 MVP 结构：三个能力 + 一个支撑项

RICE 分数会误导人把 F1 当第一优先——但 F1 只是 10 分钟的引导页。**MVP 的实质是下面三个能力，缺任一则闭环不成立。**

| 能力 | 包含 | 一句话验收 |
|------|------|-----------|
| **能力一：导入** | F5 + F3 | 用户粘贴一段 ChatGPT 生成的计划文本，40 秒内看到一份「周一 20:30：哑铃深蹲 4×12 休息 90 秒……」的日程 |
| **能力二：提醒** | F2（依赖 F1 采集时段） | 到点手机弹出通知，通知正文就是第一个动作，点开直接进执行页 |
| **能力三：执行** | F4 + F7 + F6 | 跟着做，每完成一组自动进入休息倒计时，倒计时结束提示下一组，全部做完自动打卡并给出本次完成率 |
| 支撑 | F1 | 引导不超过 5 步，可全部跳过（用默认值），全程 ≤ 60 秒 |

### 6.2 待决项：直连 AI 是否进 MVP（需 team-lead / 架构师联合定夺）

| 选项 | 论据 | 建议 |
|------|------|------|
| **A. 不进 MVP，只做粘贴导入**（PM 倾向） | ① 用户的价值缺口在「执行」不在「生成」，粘贴导入已覆盖生成需求 ② Effort 7 vs 5，且要处理 Key 存储、流式响应、错误分类、额度耗尽、端点兼容性等长尾 ③ 用户已有 ChatGPT/Claude 订阅，让他再填一次 Key 是双重付费感 ④ MVP 周期内，把 Effort 投给 F4/F7 的执行体验回报更高 | **推荐 A**。架构上保留 `PlanSource` 抽象（`paste` / `remote`），P1 直接接一个 Provider 即可，不返工 |
| B. 进 MVP | team-lead 已将其列为计划来源之一；技术上它让「生成→执行」完全在 App 内闭环，激活路径更短 | 若选 B，则 F7（图形化提示）降级为「20 个高频动作 + 其余文字要点」，以控总量 |

**决策请求**：请 team-lead 在架构师给出工作量评估后拍板。PM 建议 A，但若架构师评估 F10 可在 3 人月内完成且不挤占 F4，则 B 也可接受。

## 7. MVP 范围

### 7.1 做（P0，必须全部完成）

| ID | 功能 | 关键需求点 |
|----|------|-----------|
| F1 | 启动引导 | 5 步：① 可用器械多选（哑铃 / 弹力带 / 瑜伽垫 / 壶铃 / 单杠 / 无器械）② 运动基础单选（零基础 / 偶尔动 / 有规律训练）③ 单次可用时长（10 / 20 / 30 / 45 分钟）④ 常练时段（可多选，如 12:30、20:30）⑤ 久坐提醒开关 + 间隔（60 / 90 / 120 分钟）。全部可跳过，跳过后用默认值并允许在设置里改 |
| F5 | 粘贴导入 | 支持两条通道：**自由文本**（正则 + 规则解析：识别「4组×12次」「3×10」「休息90秒」「4 sets of 12」等模式）与 **JSON**（若识别为合法 JSON 且含动作数组，走结构化映射）。**解析结果必须先展示可编辑的校对页**：每个动作一行，可改组数/次数/休息，可删除、可拖拽排序，可整段丢弃重来。解析失败必须给出明确原因与「手动添加」出口 |
| F3 | 结构化日程引擎 | 计划 → 按周重复的日程条目。支持：按周几排布（周一/周三/周五）、休息日、单次训练的条目序列（动作 → 组 → 休息）。同一天多个训练块时按时间排序。允许「今天跳过并顺延」而不破坏后续排期 |
| F2 | 提醒 | 两种通知：① **训练提醒**（计划时段前 5 分钟，正文含首个动作与预估时长）② **久坐提醒**（工作日按间隔，正文含一个 60 秒微运动，可一键「做完」或「稍后 30 分钟」）。二者均可从通知直接深链到执行页。通知权限被拒时，App 内必须给出引导文案与降级说明（不静默失败） |
| F4 | 逐组执行引导 | 执行页同一时间只显示当前一组：动作名 + 图 + 要点 + 当前组序号（如 2/4）+ 目标次数或时长。完成一组 → 自动进入休息倒计时（大字号，可 +15s/−15s/跳过）。倒计时结束有触觉 + 声音提示。支持「这组做不动」→ 弹出三选项：降一阶 / 减一半次数 / 跳过本组（并记录跳过原因） |
| F7 | 动作图形化提示 | 60 个居家基础动作（胸/背/腿/臀/肩/核心各 10 个）各配：1 张矢量分解图（起始位与终点位）+ 3 条动作要点（文字）+ 1 条低阶替代（指向另一动作或同动作的简化形式）。未覆盖动作降级为「文字要点 + 通用占位示意」，并提示用户可切换为库内相近动作 |
| F6 | 打卡与完成率 | 按组记录「完成 / 降阶完成 / 跳过」。训练结束生成小结：本次完成率（完成组数/计划组数）、总时长、跳过原因分布。历史页按周展示完成率趋势与连续训练天数 |

### 7.2 明确不做（含原因）

| 不做 | 原因 |
|------|------|
| AI 生成计划引擎（自研模型 / 提示词工程） | 生成能力已过剩且被巨头重兵投入（Keep 自研 Keepace.ai 并已备案、Fitbod 十年算法、Hevy Trainer）。MVP 期投入产出比极低，且与「承接用户已信任的计划」这一定位自相矛盾 |
| 饮食 / 蛋白质拍照语音记录 | 用户明确排为 P1。且该场景已被薄荷健康（100 万+ 食物库、中餐适配最强）与小卡健康（免费、无广告）牢牢占据，MVP 切入等于正面硬打 |
| 视频动作指导 | 与「居家、孩子在场、不能放声音」的次画像冲突；视频带来的存储成本与首次加载时长会直接伤害「打开就开始」的核心体验。MVP 用矢量图 + 要点替代，视频留 P2 |
| 课程库 / 跟练内容 | 内容生产成本极高，且与「导入自己的计划」定位冲突。用户不需要你给他课，需要你把他的计划执行掉 |
| 社交 / 好友 / 排行榜 | 主画像是独居或小家庭的居家办公者，社交压力对他不起作用（Hevy 的社交价值建立在健身房人群）。MVP 期引入社交只会增加干扰与冷启动成本 |
| 日历双向同步（写回系统日历） | 增加权限与一致性复杂度。P1 再评估——用户已有系统日历习惯时可显著降低「忘记练」概率，是有价值的方向，但 MVP 先用本地通知 |
| Apple Watch App | 与「不要求硬件」的差异化立场冲突；且用户群中戴表比例未知。P2 作为增强 |
| 用户账号体系 / 云同步（MVP 阶段） | 单人本地优先即可闭环。引入账号会带来登录摩擦，与「60 秒内开始用」目标冲突。数据结构设计上预留 user_id 字段，P1 再开 |
| 会员 / 内购 / 定价实验 | MVP 先验证「执行闭环是否真的提升坚持率」。在数据出来前设计付费墙，容易把核心功能误关进墙里，重演 Keep 的信任崩塌 |
| 深色模式 / 多语言 / 无障碍完整合规 | 深色模式做系统跟随的自动适配（低成本），但不定制；i18n 预留接口不实现；无障碍达 WCAG 2.1 AA 基本项（键盘可达 + 对比度），不做完整审计 |

## 8. 验收标准（Given / When / Then）

### 8.1 引导与激活

- **AC-01** Given 首次安装且未完成引导，When 打开 App，Then 进入 5 步引导，允许全程「跳过」，且跳过后以默认值（无器械 / 零基础 / 20 分钟 / 20:30 / 久坐提醒开）落地到首页
- **AC-02** Given 用户在引导中选择了「哑铃、弹力带」和「20 分钟」和「20:30」，When 完成引导，Then 首页显示「今晚 20:30 · 尚未导入计划」的空状态，并有唯一主行动按钮「导入计划」
- **AC-03** Given 引导完成，When 用户冷启动 App 第二次，Then 不再出现引导，直接进入首页

### 8.2 导入（核心链路，最高优先级）

- **AC-04** Given 用户复制了 ChatGPT 生成的一段含「哑铃深蹲 4组×12次，休息90秒」的自由文本，When 粘贴到导入页并确认，Then 40 秒内（P95）展示校对页，其中一行明确显示「哑铃深蹲 / 4 组 / 12 次 / 休息 90 秒」
- **AC-05** Given 校对页显示了 5 个动作，其中第 3 个识别错误，When 用户点击该行修改组数为 3 组并保存，Then 该行更新且其它行不受影响；保存后日程使用修改后的值
- **AC-06** Given 用户粘贴的是一段无动作信息的散文，When 解析完成，Then 不报「系统错误」，而是提示「未能从这个计划里识别出动作，可以手动添加或换一段试试」，并展示「手动添加动作」入口
- **AC-07** Given 用户粘贴了合法 JSON（含 `exercises` 数组，每项有 `name/sets/reps/rest`），When 确认导入，Then 直接映射为结构，跳过正则解析，且校对页字段无错位
- **AC-08** Given 导入成功，When 用户选择「每周一、周三、周五 20:30」，Then 日程页在对应日期显示该训练，且下一次训练提醒时间为最近的周一/三/五 19:55（提前 5 分钟）
- **AC-09** Given 用户已在离线状态，When 执行导入，Then 导入与解析全部在本地完成并成功；仅在联网时尝试任何远端能力（若 F10 未启用则不涉及）

### 8.3 提醒

- **AC-10** Given 已授权通知且今天有 20:30 的训练，When 时间到 20:25，Then 收到通知，正文含「20:30 · 哑铃深蹲 4×12 等 5 个动作 · 约 20 分钟」，点击直接进入执行页
- **AC-11** Given 用户点击了久坐提醒的「稍后 30 分钟」，When 30 分钟过去且仍在工作时间，Then 再次提醒；当天累计「稍后」3 次后，第 4 次不再提醒（避免骚扰）
- **AC-12** Given 用户拒绝了通知权限，When 回到 App，Then 首页顶部出现一条说明条「未开启通知，到点不会提醒你」+「去开启」按钮；该说明条不阻塞任何功能
- **AC-13** Given 今天是休息日，When 到达久坐提醒时间，Then 仍发久坐提醒（久坐与训练无关），但不发训练提醒

### 8.4 执行

- **AC-14** Given 用户从通知进入执行页，When 页面加载完成，Then 立即显示「第 1 组 / 共 4 组」+ 动作图 + 3 条要点 + 目标「12 次」，无需任何额外点击
- **AC-15** Given 用户点按「完成这组」，When 该组标记完成，Then 自动进入休息倒计时（90 秒），倒计时用大字号显示，且有「+15 秒」「跳过休息」两个按钮
- **AC-16** Given 休息倒计时结束，When 计时归零，Then 触发触觉反馈与提示音，并自动切换到「第 2 组」执行态
- **AC-17** Given 用户在第 2 组时点按「这组做不动」，When 选择「减一半次数」，Then 该组目标变为 6 次，记录状态为「降阶完成」，且不影响第 3、4 组的目标值
- **AC-18** Given 用户中途强制退出 App，When 30 分钟内重新打开，Then 恢复到中断时的组数与剩余休息时间（误差 ≤ 2 秒），已完成组不丢失
- **AC-19** Given 用户完成最后一组的休息，When 点按「结束训练」，Then 生成小结：完成率 = 完成组数/计划组数（降阶完成计入完成），并展示跳过原因分布
- **AC-20** Given 用户完成率为 100%，When 回到首页，Then 当天该训练显示为已完成，连续训练天数 +1

### 8.5 动作提示

- **AC-21** Given 执行的动作在 60 动作库内，When 查看动作卡，Then 显示矢量分解图、3 条要点、1 条低阶替代，且文字要点可折叠
- **AC-22** Given 执行的动作不在库内，When 查看动作卡，Then 显示文字要点（若计划文本中有备注则展示备注）+ 通用占位图 + 「换个动作」入口（推荐 3 个库内相近动作）
- **AC-23** Given 用户在动作卡上点「看要点」，When 展开，Then 显示「要点」而不播放任何音频或视频

## 9. 边界条件

### 9.1 状态覆盖（五态必达）

| 状态 | 场景 | 必须呈现 |
|------|------|----------|
| Loading | 解析粘贴内容中 | 进度指示 + 已识别到的动作数递增 + 「取消」按钮；超过 5 秒展示「还在解析，内容较长」 |
| Empty | 无计划 / 今日无训练 / 无历史 | 各自独立的空状态文案 + 单一主行动按钮（导入计划 / 查看本周日程 / 完成第一次训练）。**禁止**出现 Lorem ipsum 或 "Welcome to" 类占位文案 |
| Error | 解析失败 / 通知权限被拒 / 本地存储写入失败 | 分类说明原因（不是「出错了」）+ 可执行出口（重试 / 手动添加 / 去设置）+ 不丢失用户已输入的内容 |
| Populated | 正常态 | 首页只显示「今天要做什么」，一个主行动，其余折叠 |
| Edge | 超长计划（>50 个动作）/ 极端值 / 跨周重复 | 动作数超 50 时提示「这份计划有 68 个动作，建议先导入本周的」；组数 >10 或休息 >600 秒时在导入校对页高亮提醒可能是解析错误 |

### 9.2 逐项边界

| 类别 | 边界 | 处理 |
|------|------|------|
| 空状态 | 引导跳过且无计划时直接进执行页 | 不允许。必须先进导入页 |
| 输入 | 粘贴内容为 0 字符 / 纯空白 / 超过 50KB | 0 字符时按钮置灰；超 50KB 时提示「内容过长，建议只粘贴每周的计划」并允许继续（分片解析） |
| 输入 | 只粘贴了 JSON 的片段（非法 JSON） | 降级到自由文本正则解析，不报错 |
| 数值 | 组数为 0 或次数为 0 | 校对页高亮，保存时提示「至少 1 组」，阻止保存该行但不阻止其它行 |
| 数值 | 休息时间缺失 | 默认按动作类型填（多关节 90 秒 / 单关节 60 秒 / 核心 45 秒），并在校对页标注「已自动填充」 |
| 并发 | 用户在执行训练时再次点通知进入执行页 | 恢复到当前执行态，不新建会话 |
| 并发 | 同一时段两个训练提醒 | 合并为一条：列出两个训练块名称，进入后选择 |
| 离线 | 全程离线 | 所有 P0 功能可用（导入、日程、提醒、执行、打卡），本地存储为唯一真源 |
| 时区/跨天 | 用户跨时区或 23:50 开始的训练跨过 0 点 | 训练归属到开始日期；提醒时间按设备当前时区计算；跨天时连续天数不以 0 点切分 |
| 权限拒绝 | 通知被拒 | 见 AC-12，不阻塞 |
| 权限拒绝 | 运动与健身数据（若读步数用于久坐判断）被拒 | 久坐提醒退化为「固定间隔计时」，文案中说明「无法判断你是否在动，按固定间隔提醒」 |
| 中断 | 训练中来电 / 收到其他通知 | 休息倒计时基于绝对时间戳而非累加，恢复后时间准确 |
| 中断 | 训练中低电量模式 / 后台被杀 | 状态落盘，恢复后从断点继续；已完成的组永不丢失 |
| 数据量 | 累积超过 1 年记录 | 历史页默认显示最近 8 周，更早折叠加载 |

### 9.3 非功能需求

| 类别 | 要求 | 优先级 |
|------|------|--------|
| 性能 | 冷启动到首页可交互 < 1.5s；粘贴解析 P95 < 3s（50 个动作以内）；执行页组间切换无感知延迟（< 100ms）；提醒准时率偏差 < 10s | P0 |
| 可用性 | 核心执行链路（导入→提醒→执行→打卡）离线完全可用；无任何远端依赖阻塞 P0 功能；本地数据写入失败时必须有可见提示，不静默丢数据 | P0 |
| 可靠性 | 训练中状态每完成一组即落盘；App 崩溃或被杀后恢复时数据零丢失 | P0 |
| 安全 | 全链路 HTTPS（若启用 F10）；导入内容仅在本地解析，不上传原始计划文本；不采集通讯录/位置/剪贴板历史；剪贴板读取需用户显式点按「粘贴」触发，不做后台读取 | P0 |
| 隐私 | 本地优先存储；不上报原始训练文本与健康数据；埋点仅上传聚合事件与枚举值（见 §9.4） | P0 |
| 兼容性 | iOS 16 及以上；iPhone SE（小屏 375×667）到 Pro Max 全尺寸可用；不依赖 Apple Watch | P0 |
| 可访问性 | WCAG 2.1 AA 基本项：正文对比度 ≥ 4.5:1；所有交互支持动态字体（最大档不截断关键信息）；执行页点击区域 ≥ 44×44pt；支持 VoiceOver 读出「第 2 组，共 4 组，目标 12 次」 | P1 |
| 图标方案 | 统一 SVG 图标库，具体库选型由架构师按项目锁定。**不使用 emoji 作为功能图标**（久坐提醒、导入、动作库、打卡等一律用线性 SVG 图标） | P0 |
| 视觉基调 | 参考 ai-native 规范：主色靛蓝、强调色翠绿（用于「AI 生成内容标识」与完成状态），大面积浅灰白底；每屏强调色 ≤ 2 处。**禁止紫色→粉色渐变主视觉**。动效使用 150ms 收敛缓动，禁止弹跳 | P0 |
| 国际化 | 预留 i18n 接口，MVP 仅中文 | P2 |
| 数据埋点 | 见 §9.4 | P1 |

### 9.4 数据埋点方案

MVP 必须埋点的事件（不埋则上线后无法验证「执行闭环是否真的提升坚持率」这一核心假设）：

| 类别 | 事件名 | 说明 | 关键属性 |
|------|--------|------|----------|
| 获客 | `app_launch` | 冷启动 | `source`（deeplink / icon / notification）、`version` |
| 获客 | `onboarding_step_view` / `onboarding_complete` | 引导漏斗 | `step_index`、`skipped`、`equipment_count`、`duration_bucket` |
| 激活 | `import_attempt` | 发起导入 | `channel`（text / json）、`char_count` |
| 激活 | `import_parse_result` | 解析结果 | `success`、`exercise_count`、`failed_pattern_count`、`parse_ms` |
| 激活 | `import_confirm` | 校对后确认 | `edited_rows`、`deleted_rows`、`time_to_confirm_ms` |
| 激活 | `first_workout_started` | 第一个核心操作 | `exercise_count`、`est_duration` |
| 留存 | `session_start` / `session_duration` | 使用频次 | `entry_point`、`duration_s` |
| 执行 | `workout_started` | 开始训练 | `plan_id`、`scheduled_at`、`started_on_time`（是否准点） |
| 执行 | `set_completed` | 完成一组 | `exercise_index`、`set_index`、`status`（done / downgraded / skipped）、`skip_reason` |
| 执行 | `rest_countdown_finished` | 休息结束 | `planned_rest_s`、`actual_rest_s`（衡量休息是否被打断） |
| 执行 | `workout_finished` | 完成训练 | `completion_rate`、`total_duration_s`、`downgrade_count`、`skip_count` |
| 执行 | `workout_abandoned` | 中途放弃 | `last_set_index`、`reason`（主动退出 / 无记录） |
| 提醒 | `notification_scheduled` / `notification_delivered` / `notification_opened` | 提醒链路 | `type`（workout / sedentary）、`lead_min`、`deep_link_ok` |
| 提醒 | `sedentary_snooze` | 久坐提醒稍后 | `snooze_count_today` |
| 转化 | 本期不埋 | MVP 无付费墙 | — |
| 异常 | `parse_error` / `storage_write_failed` / `permission_denied` | 异常 | `error_type`、`context`、`version` |

**实现规范**
- 事件命名：`{对象}_{动作}`，全小写 + 下划线（如 `import_parse_result`）
- 每个事件固定附带：`user_local_id`（本地生成的匿名 ID，非账号）、`timestamp`、`device_model`、`os_version`、`app_version`
- **不上报**：原始计划文本、动作库内的完整备注明细、任何可反推个人身份的信息、IP 地址
- 提供「关闭数据分析」开关（设置内），关闭后仅保留本地记录

## 10. 成功指标

### 10.1 北极星指标

> **W1 训练执行完成率 = 已完成的组数 / 计划组数**（首次使用后 7 天内，所有已开始的训练）

选它的理由：这是唯一能同时验证「计划可用」和「用户真的在做」的指标。它下降就意味着导入的解析质量有问题，或降级机制没解决「做不动」。

### 10.2 分层指标

| 层 | 指标 | MVP 目标（上线 8 周内） | 为什么是这个值 |
|----|------|------------------------|----------------|
| 激活 | 完成引导 → 成功导入计划的比例（导入转化率） | ≥ 55% | 粘贴导入的摩擦是本产品最大漏斗风险，55% 是可接受下限；低于 40% 说明必须把 F10 直连 AI 提前 |
| 激活 | 引导完成率 | ≥ 80% | 5 步引导，全部可跳过，不应低于此 |
| 激活 | 首次导入耗时中位数 | ≤ 90 秒 | 从进入导入页到确认保存 |
| 核心价值 | 计划导入后第 14 天仍在使用的比例（计划保鲜率） | ≥ 50% | 对标「ChatGPT 计划三周就死」，这是差异化是否成立的判决指标 |
| 核心价值 | W1 训练执行完成率 | ≥ 80% | 低于 70% 说明计划与能力不匹配，需上线 F8/F9 |
| 核心价值 | 准点开始率（在计划时段 ±30 分钟内开始训练） | ≥ 60% | 衡量提醒是否真的起作用；若低于 40%，提醒设计（文案/时机/久坐联动）需重做 |
| 留存 | D7 留存 | ≥ 35% | 单人工具类 App 的合理水平 |
| 留存 | 周活跃训练天数中位数 | ≥ 2 天/周 | 主画像自述可执行 3 天/周，取 2 为可接受下限 |
| 体验质量 | 粘贴解析成功率（无需手动大改即可确认） | ≥ 75% | 低于此值，导入体验不成立，需重做解析规则 |
| 体验质量 | 训练中途放弃率 | ≤ 20% | 高于 30% 说明单次训练时长或强度设计有问题 |
| 体验质量 | 崩溃率 / 训练中数据丢失次数 | 崩溃率 < 0.5%；数据丢失 **0** | 数据丢失是零容忍项（Keep 的差评证明这一点） |

## 11. 风险

| ID | 风险 | 可能性 | 影响 | 缓解措施 |
|----|------|--------|------|----------|
| R1 | **粘贴导入摩擦导致激活失败**——用户不想切 App 复制，或不知道复制什么 | 高 | 高（直接决定产品是否成立） | ① 导入页内置「怎么从 ChatGPT / Claude 复制计划」的三步图示 ② 提供可复制的示例提示词（让用户回 AI 里问一句就得到可解析的格式）③ 解析失败时永不空手：必给手动添加出口 ④ 设置阈值 KPI（导入转化率 < 40%）触发 F10 提前 |
| R2 | **解析准确性不足**——中文/英文/各式格式的动作描述千奇百怪，正则覆盖不住 | 高 | 高 | ① 双通道（文本规则 + JSON 结构化），并主动在示例提示词里引导用户要 JSON ② 校对页是设计核心而非附属，必须好用 ③ 建立解析失败样本库，MVP 后持续补规则 |
| R3 | **「60 个动作图」的生产成本与质量**——矢量图数量不足会直接削弱差异化，质量差会显得廉价 | 中 | 中 | ① MVP 只覆盖居家最常见的 60 个（不含器械复合动作）② 未覆盖动作有明确降级路径，不阻塞 ③ 图必须自制或获得明确授权，不挪用来源不明素材 |
| R4 | **用户根本没有 AI 生成的计划**——主画像假设他已经在用 AI 排计划，但可能只是一时兴起 | 中 | 高 | ① 上线前用 10 人访谈验证「近 3 个月是否让 AI 排过计划、是否执行过」② 若验证不足，把内置示例计划（3 套，按器械/时长分）作为即时可用的兜底入口，降低首次使用门槛 |
| R5 | **提醒被系统或用户习惯吞掉**——iOS 专注模式、低电量模式、通知折叠会让提醒失效 | 中 | 中 | ① 通知用「时效性」级别（time-sensitive）以穿透专注模式 ② App 内提供通知健康自检 ③ 埋点 `notification_delivered` vs `notification_opened` 分离监控 |
| R6 | **单点价值太薄，被巨头的免费功能吃掉**——Keep 或 Hevy 加一个「导入计划」功能，动刻就没有护城河 | 中 | 高 | ① 承认这是真实风险，MVP 目标是验证假设而非建护城河 ② 若验证成立，护城河来自「解析质量 + 执行体验细节 + 用户历史数据」，需在 P1 加速积累跨会话训练历史（这是 AI 计划的死穴） |
| R7 | **直连 AI（F10）引入 Key 安全与合规风险**——用户 API Key 存储、额度消耗纠纷、端点兼容性长尾 | 中 | 中 | ① Key 存 iOS Keychain，绝不明文落盘或上传 ② 明确说明「你的 Key 只存在本机，消耗的是你自己的额度」③ 若选 B 方案，必须做清晰的额度耗尽与 401/403 错误分类 |
| R8 | **提醒变成骚扰，导致用户关权限后彻底流失** | 中 | 中 | ① 久坐提醒「稍后」上限 3 次 ② 训练提醒每日最多 1 次主提醒（+1 次补提醒，用户可关）③ 连续 5 天忽略训练提醒后，自动降低频率并提示用户调整时段 |
| R9 | **训练中被打断导致数据丢失**（居家办公真实高频场景） | 中 | 高 | 见 §9.2「中断」两项 + 可靠性零容忍指标 |
